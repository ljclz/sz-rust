## 3. 红队点名 3 处逐一判定

### 3.1 sso.rs:1179 `tokio::time::sleep(Duration::from_secs(35))`

**文件路径**：`packages/sz-rust-auth-facade/src/sso.rs:1179`
**所在函数**：`test_validate_with_renewal_triggers`（`#[tokio::test]`，`#[cfg(test)]` 模块内，测试代码）
**上下文**：
```rust
// sso.rs:1156-1162 — 配置：access_token_ttl=60s, renewal_threshold=30s
sso.with_renewal_config(RenewalConfig {
    enabled: true,
    renewal_threshold: chrono::Duration::seconds(30),
    renewal_ratio: 0.2,
    access_token_ttl: chrono::Duration::seconds(60),
});
// sso.rs:1177-1189 — sleep 35s 后验证 token 续期触发
let login_resp = sso.login("user1", "pass1").await.unwrap();
tokio::time::sleep(tokio::time::Duration::from_secs(35)).await;  // ← 本处
let (claims, renewed) = sso.validate_with_renewal(&login_resp.tokens.access_token).await.unwrap();
assert!(renewed.is_some());  // 35s 后剩余 25s < 30s 阈值 → 触发 renewal
```

**判定**：**可优化（保留 + 标注 flaky 风险低）**

**理由**：
- 测试代码（`#[cfg(test)]`），不违反铁律 4。
- sleep 35s 是等待 token 进入续期窗口的确定性状态等待：TTL=60s，threshold=30s，35s 后剩余 25s < 30s 阈值，触发 renewal。
- **flaky 风险评估**：缓冲 = 35s - 30s = 5s。在正常负载下 5s 缓冲足够，但在 CI 高负载/容器 CPU 限流场景下，`login` + `validate_with_renewal` 的执行时间若累计超过 5s 偏移，可能导致 token 剩余时间恰好跨过阈值边界。风险等级：**低**。
- **优化建议**：引入 `MockClock`（如 `sz-rust-ai-facade/tests/common/mock_clock.rs` 已有的模式）替代真实 sleep，将 35s 等待转为瞬时时间推进。优化优先级：**P3**（风险低，且 mock 时间需重构 `SsoService` 时间源）。
- **处置决定**：**保留**，在报告中标注为 P3 可优化项。不阻塞 P1-3 升级。

### 3.2 slow_call_breaker.rs:312 `std::thread::sleep(Duration::from_millis(30))`

**文件路径**：`packages/sz-rust-api-gateway/src/slow_call_breaker.rs:312`
**所在函数**：`test_breaker_recovery_to_half_open`（`#[test]`，`#[cfg(test)]` 模块内，测试代码）
**上下文**：

**判定**：**合理保留**

**理由**：

- **处置决定**：**保留**，无需修复。

### 5.2 P2-4（panic! 当断言）—— 可从"部分修复"升级为"已修复（含 P3 风格优化项）"
