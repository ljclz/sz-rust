## 4. 意外发现 A：grace-period 告警按请求落盘（V，已修 + 已复测）

评测与整改都聚焦在 `info!`/`debug!`，漏了这一条：**每个业务请求各写一行 WARN**。

- 现场计数（release 修复前那次运行留下的日志）：
  - 总日志 157,774 行 / 49,838,168 B
  - 其中 WARN 157,369 行 / **49,726,841 B = 全部日志字节的 99.78%**
  - 消息 `无 aud 旧令牌在 grace period 内放行，建议轮换` 独占 **157,068 行**，来源 `sz_rust_sz300::services::auth_service::audience`
  - 业务请求数 152,068（+ 冒烟 4,640）→ 即「一次请求一行 WARN」，单行 193–316 B
- 触发条件：门禁签发的 JWT **不含 `aud`**（`scripts/perf-regression.js::mintJwt` 的 claims 为 `sub/exp/iat/user_id/roles/permissions/token_use`），走 `auth_service.rs` 的 grace-period 分支（`grace_period_secs = 2592000`）。任何无 `aud` 的历史令牌都会命中；`SZ300_PERF_*` 之外的真实遗留令牌同样会。
- 影响量化：压测 10 分钟量级写掉 **≈47 MB**；且该分支是**按请求计费**的磁盘 I/O 与序列化开销，属于「可被最小成本放大的输出面」——持有无 `aud` 令牌的客户端能用它把日志盘灌满。
- 修复：`packages/sz-rust-sz300/src/services/auth_service.rs`（`audience::WarnSampler`，窗口常量 `WARN_SAMPLE_INTERVAL_SECS = 60`），同一 60 s 窗口只输出一条，并携带 `suppressed_in_window` 计数（安全信号不丢）。同步 `middleware/auth_middleware.rs` 的文档注释（规则 19 文档-代码一致）。
- 单测：`services::auth_service::tests::test_no_audience_warning_is_sampled_per_window` → `1 passed`（窗口首条输出 / 窗口内 9 次静默 / 下条输出携带 9 / 再下窗口携带 1）
- 复测（同一 seed 库、同一门禁、c=50 / 预热 5 s / 60 s × 1，**debug 档二进制**——只用于统计日志条数，不用于任何性能结论；**release 档复测见 §11.4**）：

| 指标 | 修复前（release） | 修复后（debug，release 见 §11.4） |
|---|---|---|
| 业务请求数 | 156,708 | 83,067 |
| `无 aud…` WARN 行数 | 157,068 | **3**（每 60 s 一条，`suppressed_in_window` = 0 / 40,262 / 36,423） |
| 日志总字节 | 49,838,168 | **3,149** |
| 日志总行数 | 157,774 | 14 |

`suppressed_in_window` 求和 = 76,685，与 §4 业务请求数量级一致（窗口边界外的请求落入未输出部分），说明**没有丢事件、只丢了重复**。

### 6.2 SQL 层 `EXPLAIN ANALYZE`（20,000 行数据集，MySQL 9.6 容器内）

| 查询 | 实测 |
|---|---|
| `SELECT COUNT(*) FROM order WHERE merchant_id=1` | 总 **6.31 ms**；覆盖索引 `idx_merchant` 扫 **20,000** 个索引项耗时 5.2 ms |
| `SELECT ... FROM order WHERE merchant_id=1 ORDER BY order_id DESC LIMIT 20 OFFSET 0` | **4.89 ms**（`idx_merchant` 反向扫描取 20 行，`FORCE INDEX` 生效） |
| `SELECT COUNT(*) FROM good WHERE merchant_id=1` | 总 **6.19 ms**；覆盖索引扫 20,000 项 4.95 ms |

→ 业务请求的 DB 侧 ≈11 ms 中，**`COUNT(*)` 占 5.2–6.3 ms（≈47–57%）**，且随表行数线性增长（O(N)）。这为 31–60 天项「`COUNT` 缓存/近似 + keyset 分页」给出首个同机同数据集的量化依据。
