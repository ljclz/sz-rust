## 4. 意外发现 A：grace-period 告警按请求落盘（V，已修 + 已复测）

评测与整改都聚焦在 `info!`/`debug!`，漏了这一条：**每个业务请求各写一行 WARN**。

- 现场计数（release 修复前那次运行留下的日志）：
  - 总日志 157,774 行 / 49,838,168 B
  - 其中 WARN 157,369 行 / **49,726,841 B = 全部日志字节的 99.78%**
  - 消息 `无 aud 旧令牌在 grace period 内放行，建议轮换` 独占 **157,068 行**，来源 `sz_rust_sz300::services::auth_service::audience`
  - 业务请求数 152,068（+ 冒烟 4,640）→ 即「一次请求一行 WARN」，单行 193–316 B
- 触发条件：门禁签发的 JWT **不含 `aud`**（`scripts/perf-regression.js::mintJwt` 的 claims 为 `sub/exp/iat/user_id/roles/permissions/token_use`），走 `auth_service.rs` 的 grace-period 分支（`grace_period_secs = 2592000`）。任何无 `aud` 的历史令牌都会命中；`SZ300_PERF_*` 之外的真实遗留令牌同样会。
- 影响量化：压测 10 分钟量级写掉 **≈47 MB**；且该分支是**按请求计费**的磁盘 I/O 与序列化开销，属于「可被最小成本放大的输出面」——持有无 `aud` 令牌的客户端能用它把日志盘灌满。
- 修复：`packages/sz-rust-sz300/src/services/auth_service.rs`（`audience::WarnSampler`，窗口常量 `WARN_SAMPLE_INTERVAL_SECS = 60`），同一 60 s 窗口只输出一条，并携带 `suppressed_in_window` 计数（安全信号不丢）。同步 `middleware/auth_middleware.rs` 的文档注释（规则 19 文档-代码一致）。
- 单测：`services::auth_service::tests::test_no_audience_warning_is_sampled_per_window` → `1 passed`（窗口首条输出 / 窗口内 9 次静默 / 下条输出携带 9 / 再下窗口携带 1）
- 复测（同一 seed 库、同一门禁、c=50 / 预热 5 s / 60 s × 1，**debug 档二进制**——只用于统计日志条数，不用于任何性能结论；**release 档复测见 §11.4**）：

| 指标 | 修复前（release） | 修复后（debug，release 见 §11.4） |
|---|---|---|
| 业务请求数 | 156,708 | 83,067 |
| `无 aud…` WARN 行数 | 157,068 | **3**（每 60 s 一条，`suppressed_in_window` = 0 / 40,262 / 36,423） |
| 日志总字节 | 49,838,168 | **3,149** |
| 日志总行数 | 157,774 | 14 |

`suppressed_in_window` 求和 = 76,685，与 §4 业务请求数量级一致（窗口边界外的请求落入未输出部分），说明**没有丢事件、只丢了重复**。

### 6.2 SQL 层 `EXPLAIN ANALYZE`（20,000 行数据集，MySQL 9.6 容器内）

| 查询 | 实测 |
|---|---|
| `SELECT COUNT(*) FROM order WHERE merchant_id=1` | 总 **6.31 ms**；覆盖索引 `idx_merchant` 扫 **20,000** 个索引项耗时 5.2 ms |
| `SELECT ... FROM order WHERE merchant_id=1 ORDER BY order_id DESC LIMIT 20 OFFSET 0` | **4.89 ms**（`idx_merchant` 反向扫描取 20 行，`FORCE INDEX` 生效） |
| `SELECT COUNT(*) FROM good WHERE merchant_id=1` | 总 **6.19 ms**；覆盖索引扫 20,000 项 4.95 ms |

→ 业务请求的 DB 侧 ≈11 ms 中，**`COUNT(*)` 占 5.2–6.3 ms（≈47–57%）**，且随表行数线性增长（O(N)）。这为 31–60 天项「`COUNT` 缓存/近似 + keyset 分页」给出首个同机同数据集的量化依据。

## 16. 响应 gzip 压缩与令牌端点 BREACH 排除（ADR-050，2026-10-30）

31–60 天路线项「开 gzip/brotli（注意 BREACH）」落地，详见 `docs/adr/0050-响应gzip压缩与breach排除.md`。

- **改动**：新增 `packages/sz-rust-sz300/src/middleware/compression.rs` —— `compression_layer()` 返回 `CompressionLayer<And<DefaultPredicate, PredicateFn>>`，谓词 = tower-http 默认（`SizeAbove(32)` ∧ 排除 gRPC / 图片 / **SSE**）再 `.and(not_marked)`；`not_marked` 检查响应扩展里有没有 `NoCompression` 标记。`mark_no_compress` 是路由级 `from_fn` 中间件，跑完内部 handler 后给响应 `extensions_mut().insert(NoCompression)`。接线在 `create_router` 的 `.with_state` 之后按 `config::compression_enabled()`（`SZ300_COMPRESSION`）决定是否 `.layer(compression_layer())`，压缩层位于 `DataMaskLayer` 外侧。
- **BREACH 依据（代码取证）**：`controllers/auth.rs:105` 登录成功响应同时携带**新签发的 `token` / `refresh_token`** 与**回显的请求 `username`**，即「密文 + 攻击者可影响且重复出现的明文」同处一个响应体，正是 BREACH 的成立前提。因此 `/api/v1/auth/login` 与 `/api/v1/auth/refresh` 在 RBAC 与非 RBAC 两条建路由分支上都单独挂 `mark_no_compress`。
- **为什么用响应扩展而不是路径判断**：tower-http 的 `Predicate::should_compress` 签名只拿得到 `StatusCode / Version / HeaderMap / Extensions`，**拿不到请求 URI**，在谓词里按路径排除需要自定义 `map_response` 前置层；把「不压缩」作为响应的一个属性由路由声明、经扩展向下传递，改动面最小且无需替换 `CompressionBody`。标记能穿透 `DataMaskLayer` 的原因是脱敏层用 `Response::from_parts` 重建响应（保留扩展）。
- **为什么默认关闭**：① 本项影响出口字节数与 CPU，属于「改变性能基线语义」的默认值，未实测就默认开启违反本记录的证据分级约束；② 现有基线（`packages/sz-rust-benchmark-suite/benches/baseline.json`）与 `scripts/perf-regression.js` 的 `headersFor()` **不发 `Accept-Encoding`**，默认开启会让「基线不变」的结论与被压缩的真实生产流量不可比；③ 开关同时是同源 A/B 的前提——同一二进制用环境变量开/关对比，不需要两个构建产物。
- **为什么只做 gzip 不做 brotli**：`compression-codecs` 当前仅以 `flate2` 编解码进入构建图，`compression-br` 需引入 `brotli`（Cargo.lock 里的 8.0.4 只来自 `tauri-codegen`，不在 sz300 依赖链上）；在收益未实测的前提下叠加「新依赖 + 第二种算法的 CPU/压缩率权衡」会使归因不可能。
- **单测（T）**：`cargo test -p sz-rust-sz300 --lib` = **118 passed**（+2：`not_marked` 只排除被标记的响应 / `compression_layer()` 可构造）；`config_test` = **7 passed**（新增开关用例：未设置→false，`1/true/TRUE/yes/on` 及带空格→true，`0/false/no/off`→false，`maybe`→false 即 fail-closed）。
- **离线集成（T，无需数据库）**：`cargo test -p sz-rust-sz300 --test compression_test` = **5 passed**。测试按生产层序组装同一棵 `Router`（route → `DataMaskLayer` → `compression_layer()`），用 `router.oneshot()` 直接驱动：大 JSON 响应返回 `content-encoding: gzip` 且 body 以 `0x1f 0x8b` 开头、长度小于原 JSON；`/auth/login` 响应**无** `content-encoding` 且明文含测试 SKU（证明标记确实生效而非「恰好没压」）；小响应与 `text/event-stream` 均不压缩；不带 `Accept-Encoding` 的请求回退 identity。断言用 magic-byte + 子串而非全等，因为脱敏层会重新序列化 JSON（不保留 fixture 尾部空格）。

### 17.7 顺带发现（测量卫生，W→建议项）

每腿（预热 10 s + 稳态 180 s）在 `RUST_LOG=info` 下产生 **200–320 MB** 服务日志（`leg_end server_log_bytes`：A 220,623,177 / B 246,296,267 / A2 200,167,565 / B2 290,409,274 / C2 318,370,220 / D2 319,942,047），即约 25 MB/min。这正是首轮批次里 `MsMpEng`（Defender 实时扫描）长时间高 CPU 的来源，也放大了复测窗口等待时间。建议：门禁压测期把访问日志降到 `warn`（或与 §10 业务热路径日志降级同批处理），属测量卫生而非产品缺陷。
