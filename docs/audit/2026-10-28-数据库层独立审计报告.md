## 1. 一句话结论 + 评分 + 生产结论

> **数据层当前是一套"能演示、不能承载交易"的原型：主业务库零显式事务、零外键、零 CHECK，测试用的是另一套手工捏造的 Schema，迁移器在 PostgreSQL 上必然失败且把失败写进了断言。**

**总分 40 / 100，等级 D（原型级，不可承载生产数据）。**

三条硬阻断（任一即可否决上线）：

1. 商户列表在生产 DDL 上必报 `Unknown column 'merchant_name'`
   —— [merchant_service.rs:88](../../packages/sz-rust-sz300/src/services/merchant_service.rs#L88) 查询 `merchant_name`，而生产表 [001_init.sql](../../packages/sz-rust-sz300/migrations/001_init.sql) 中列名为 `name`；该接口已挂路由 `[W]` [router.rs:121](../../packages/sz-rust-sz300/src/router.rs#L121)。
2. MQTT 落单用 `CONCAT('O', UNIX_TIMESTAMP())` 生成订单号（秒级）
   —— [mqtt_service.rs:158](../../packages/sz-rust-sz300/src/services/mqtt_service.rs#L158) `[W]`，全系统同秒多单必撞 `UNIQUE(order_no)`。
3. 下单头 + 行无事务、行插入失败被 `tracing::error!` 吞掉
   —— [order_service.rs:226-268](../../packages/sz-rust-sz300/src/services/order_service.rs#L226) `[W]`；`packages/sz-rust-sz300/src` 全目录 `begin_transaction|commit()|rollback()` 命中数 = **0**（`[V]`，见附录 A-3）。

**可执行 DDL（均标注锁风险，禁止直接在生产执行）**

```sql
-- DDL-2  PG：补唯一约束与高频索引（CONCURRENTLY 不阻塞写；失败不回滚，需人工清理）
CREATE UNIQUE INDEX CONCURRENTLY IF NOT EXISTS uq_device_sn ON device (device_sn);
CREATE UNIQUE INDEX CONCURRENTLY IF NOT EXISTS uq_order_no  ON "order" (order_no);
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_order_merchant_created ON "order" (merchant_id, created_at DESC);

-- DDL-2' MySQL：二级索引可在线加（INPLACE / LOCK=NONE）；有重复值会直接失败
ALTER TABLE `device` ADD UNIQUE KEY uk_device_sn (device_sn), ALGORITHM=INPLACE, LOCK=NONE;
ALTER TABLE `order`  ADD KEY idx_merchant_created (merchant_id, created_at), ALGORITHM=INPLACE, LOCK=NONE;

-- DDL-4  status 约束（MySQL 8.0.16+ 才真正强制；ADD CHECK 部分版本会重建表 → 锁风险高，建议低峰）
ALTER TABLE `order`
  ADD CONSTRAINT chk_order_status CHECK (status IN (0,1,2,3)),
  ALGORITHM=COPY;   -- 显式标注：重建整表，期间写入阻塞

-- DDL-5  外键（InnoDB 加 FK 需 COPY 重建 + 阻塞写；必须先在低峰且确认无孤儿）
DELETE oi FROM order_item oi LEFT JOIN `order` o ON oi.order_id = o.order_id WHERE o.order_id IS NULL;
ALTER TABLE order_item
  ADD CONSTRAINT fk_oi_order FOREIGN KEY (order_id) REFERENCES `order`(order_id) ON DELETE CASCADE,
  ALGORITHM=COPY;

-- DDL-7  marketplace 金额改整数分（PG：整表重写 + AccessExclusive，必须停机窗口）
ALTER TABLE plugins ALTER COLUMN price TYPE BIGINT USING (round(price * 100))::BIGINT;
ALTER TABLE plugins ADD CONSTRAINT chk_plugins_price_nonneg CHECK (price >= 0);

-- DDL-8  时间列统一 UTC（示例：MySQL 8，ALTER 会重建表；TIMESTAMP 有 2038 上限，需评估）
-- ALTER TABLE `order` MODIFY created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP;

-- DDL-9  保留字改名（PG 元数据变更，ACCESS EXCLUSIVE 但极短）
ALTER TABLE configs RENAME COLUMN key TO config_key;
```

## 6. 性能（EXPLAIN 未验证 + 静态索引映射）

> **EXPLAIN 未验证**。原因：禁止对非一次性环境执行 DDL/migrate，本机亦无可用实例；且启动数据库需先征得同意。以下为"查询—索引"静态映射，**不作为达标证据**。

| 生产查询（`[W]`） | 过滤/排序 | 现有索引 | 判定 |
|---|---|---|---|
| `order` 列表（merchant_id + status + created_at 区间，ORDER BY order_id DESC） | 3 列 + 排序 | `idx_merchant`、`idx_status`、`idx_created`（各自单列） | ⚠️ 只能选一个，其余回表过滤；建议 `(merchant_id, created_at)` |
| `order` 列表（device_id + status） | 2 列 | `idx_device` | ⚠️ 建议 `(device_id, status)` |
| `order_item WHERE order_id = ?` | 单列 | `idx_order` | ✅ |
| `good` 列表（merchant_id + status，ORDER BY good_id） | 2 列 | `idx_merchant` | ✅ 基本可覆盖（status 残余过滤） |
| `device WHERE device_sn = ?` | 唯一 | UNIQUE | ✅ |
| `merchant` 列表（ORDER BY merchant_id） | 排序 | PK | ✅ |
| `operate_log`（merchant_id + created_at DESC） | 2 列 | `idx_merchant`/`idx_created` | ⚠️ 建议复合 |
| `sz_dtx_log WHERE state='running'` | 单列 | `idx_state` | ✅ |
| marketplace `plugins` 按 tags | 数组 | GIN | ✅ |

**深分页**：`offset = (page-1)*page_size`，第 10 000 页（20 条/页）需扫描 200 000 行后丢弃；MySQL 无延迟关联优化。

**N+1 写**：下单 N 个商品 = N 条 INSERT（P1-6）。

**可观测性缺口**（`[V]` grep 全仓无命中）：

- `slow-query-capture` / `slow_query_guard` 未在任何 `Cargo.toml` 启用 → 无慢查询日志；
- `db_pool_collector` 只有 trait 定义，sz300 未实现 → 无池指标；
- 无 DB 延迟直方图/错误率面板。

改造建议（按收益排序）：① 复合索引补齐（DDL-2）；② 深分页改 keyset；③ 批量插入；④ 启用慢查询采集（阈值 200 ms，采样 1%）；⑤ 池指标接入 `/metrics`。

## 9. 横向对比：Rust / C++ / C#，保留还是推翻

### 9.1 如果重写，保留什么

| 保留 | 理由 |
|---|---|
| 显式 SQL + 参数化绑定 | 4 个 service 的写法是正确的数据库工程实践 |
| 显式列投影（禁 `SELECT *`） | 抗 Schema 变更 |
| `Result` 链式错误 + 超时包装 | 比异常体系更可控 |
| 编译期类型检查（`sqlx::query!` 可离线校验 SQL） | 建议真正启用，而非字符串 |
| 单二进制部署 | 运维成本低 |

### 9.2 推翻什么

| 推翻 | 理由 |
|---|---|
| 自研 `AnyPool` 运行时多态 + 双层池 | 每次多库适配都要手写占位符/类型映射，本次 PG 故障即由此产生 |
| 自研迁移器（忽略方言、无校验和、无锁） | 直接换 `sqlx::migrate!` 或 Flyway/Liquibase |
| 进程内 LRU 查询缓存 | 多实例下必然不一致；用 Redis |
| 手写测试 DDL | 测试必须跑真实 migrations |
| 5 引擎全支持的目标 | 没有 CI 验证的"支持"等于负债；先砍到 MySQL（+PG） |

### 9.3 语言对比

| 维度 | Rust（现状） | Rust（精简后） | C++ | C# |
|---|---|---|---|---|
| 运行时安全 | 高 | 高 | 低（悬垂/泄漏） | 高 |
| 数据层生态 | 弱（sqlx 尚可，ORM 不成熟） | 足够 | 很弱（libpqxx/SOCI 手写为主） | **最强**（EF Core + Dapper + Npgsql） |
| 迁移工具 | 自研（缺陷多） | sqlx-migrate（够用） | 基本靠外部 | EF Migrations / Flyway |
| 异步成熟度 | 中（Tokio） | 中 | 低 | 高（async/await 完整） |
| 性能上限 | 高 | 高 | 最高 | 中高 |
| 招聘/维护 | 难 | 难 | 中 | 易 |

**结论**：

- **不建议为数据层改用 C++**——同样的正确性问题在 C++ 里只会更难保证，且 ORM/迁移生态更差。
- **如果团队是 .NET 背景，C# + EF Core/Dapper 能在更短时间内得到一个"正确"的数据层**，这是本报告唯一认为值得考虑的换语言场景。
- **Rust 的优势成立的前提是"保持简单"**：sqlx + 官方 migrate + 手写 SQL。当前这套自研抽象栈恰好抵消了 Rust 的安全收益，反而制造了 PG/Oracle/MSSQL 的隐性缺陷。
