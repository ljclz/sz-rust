## 二、攻击载荷细节与预期响应

### A1 JWT alg 混淆
```
载荷：将 token 头改为 {"alg":"none","typ":"JWT"} 后截断签名
预期：verify_token 检查 header.alg != "HS256" → 拒绝（sz-orm-auth jwt.rs:171）
```

### A2 JWT 弱密钥
```
载荷：用短密钥（如 "123456"）签 token
预期：服务无法启动（validate_jwt_config panic，M-3 修复）
```

### A3 JWT 过期重放
```
载荷：截获 token 改 exp 为过去时间
预期：claims.is_expired() → TokenExpired 错误
```

### A4 Bearer 解析绕过
```
载荷：Authorization: "bearer <token>" / "Bearer  <token>" / "BEARER<token>"
预期：extract_bearer_token 大小写不敏感剥离（L-3）；无前缀时透传由 verify 兜底
```

### A5 公开路径绕过
```
载荷：/health/（尾斜杠）、//api/v1/auth/login（双斜杠）、/api/v1/auth/login%2f
预期：is_public_path 精确匹配（contains 检查），均不匹配 → 走鉴权
```

### A6 IDOR 横向越权
```
载荷：POST /api/v1/order/list {"merchant_id": 1}（受害者商户）
预期：resolve_merchant_id 用 JWT user_id 反查归属 → 服务端覆盖/拒绝（H-1）
```

### A7 缓存投毒
```
载荷：商户 A 请求 /api/v1/product/list（写缓存）→ 商户 B 同 page 请求
预期：缓存 key 含 merchant_id → 不同 key 不共享（H-1）
```

### A8 SQL 注入
```
载荷：keyword="' OR 1=1 --"、merchant_id=1;DROP TABLE good
预期：所有值走 ? 占位符参数化；where_clause 仅固定条件名
```

### A9 MQTT 伪造
```
载荷：topic="/sz/device/../../etc/status"、payload 1MB
预期：device_sn 格式校验拒绝（含 / 等）→ 丢弃；payload >256KB 丢弃（L-1）
```

### A10 上传欺骗
```
载荷：filename="x.jpg" body="<script>alert(1)</script>"
预期：magic_bytes_match 失败 → 拒绝（M-4）
```

### A11 超大 body DoS
```
载荷：POST 1GB body
预期：axum::body::to_bytes(body, 1MB) → 错误（H-2）
```

### A12 限流绕过
```
载荷：轮换 X-Forwarded-For 值
预期：trust_proxy_headers=false → 全部归 "unknown" 统一限流（M-2）
```

### A13 AI 成本攻击
```
载荷：prompt 100KB / model="gpt-4o-expensive"
预期：prompt >16000 拒绝；model 非白名单拒绝（M-1）
```

### A14 错误枚举
```
载荷：登录不存在的用户 vs 密码错误
预期：统一 "用户名或密码错误"（无枚举差异）
```

### A15 信息泄露
```
载荷：GET /metrics（未认证）
预期：公开路径仅 /health* 和 /metrics 明确列入——需复核 metrics 是否应公开
```

### A16 业务逻辑（待专项）
```
载荷：total_fen=-1、status 跳变、并发重复提交
预期：服务端应校验金额非负 + 状态机约束
```

## 三、复核方法

1. **代码证据优先**：每个攻击载荷 → 追踪代码路径 → 确认拦截点存在且逻辑正确
2. **绕过变体测试**：对每个拦截点尝试 2-3 种变体（大小写/编码/路径归一化）
3. **修复有效性判定**：✅ 拦截有效 / ⚠️ 部分有效（有绕过变体）/ ❌ 可绕过
4. **动态渗透**：待 sz300 可运行环境（MySQL/PG/MQTT）就绪后，用 curl 实际执行 PoC
