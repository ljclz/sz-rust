**结论**：当前 OpenAPI spec 是「半完整契约」——有路径清单 + 状态码 + 部分请求体，但缺响应体 schema。可被第三方工具（Swagger Editor / openapi-generator / Redocly）校验语法有效性，但无法用于 response body 契约验证。

## 2. 评估维度分析

### 2.1 当前覆盖：OpenAPI-路由一致性门禁是否已覆盖契约测试核心场景？

**部分覆盖，但有显著缺口**。

| 契约测试核心场景 | 当前覆盖 | 证据 |
|------------------|----------|------|
| 路由清单一致性（路径增删漂移） | ✅ 已覆盖 | `scripts/audit/openapi-consistency.js:34-55` |
| 状态码契约（特定端点） | ⚠️ 部分覆盖 | `login_contract_test.rs:1-118`（仅 login 端点 400/401） |
| request body schema 校验 | ❌ 未覆盖 | OpenAPI 注册了 login request body（`openapi.rs:98-106`），但无自动化测试验证实际请求体是否符合 |
| response body schema 校验 | ❌ 未覆盖 | OpenAPI 未注册 response body schema，无自动化测试 |
| 字段类型不匹配 | ❌ 未覆盖 | 无 schema 校验 |
| 必填字段缺失 | ❌ 未覆盖 | 无 schema 校验 |
| 跨端点契约一致性（如所有 list 端点分页参数一致） | ❌ 未覆盖 | 无 |

**结论**：当前门禁覆盖了契约测试的「路径清单」层，但**未覆盖** schema 层（字段类型/必填/响应体结构）。这是契约测试能捕获缺陷的主要层面，当前为缺口。

### 2.2 consumer-driven 需求：项目是否有多个 API 消费方需要 consumer-driven contract？

**有多端消费方，但均在独立仓库**。

| 消费方 | 仓库位置 | 是否可在本仓库做 consumer-driven |
|--------|----------|------------------------------|
| Vue H5 前端 | `D:\vue\test\sz-work`（独立仓库） | ❌ 跨仓库 |
| Tauri 桌面 | `packages/sz-rust-visual`（本仓库 Tauri 壳，前端 UI 在 Tauri Webview 层） | ⚠️ 壳在本仓库，但 UI 代码属前端层 |
| 小程序 | 外部 | ❌ 跨仓库 |
| Android | 外部 | ❌ 跨仓库 |
| API 网关 | `packages/sz-rust-api-gateway`（本仓库） | ⚠️ 透明转发，不解析 body，契约收益低 |

**结论**：consumer-driven contract 测试的核心理念是「consumer 写契约，provider 验证」。本仓库是 provider，主要 consumer 在独立仓库。在本仓库内做 consumer-driven contract 测试**违背其设计理念**——应由前端仓库（consumer）写 pact 契约，发布到 pact broker，本仓库（provider）从 broker 拉取契约验证。这需要跨仓库协同基础设施（pact broker），超出本仓库范围。

### 2.3 引入成本：Rust 生态 pact 成熟度与 CI 复杂度

**Rust 生态 pact 方案不成熟，引入成本高**。详见 §3。

### 2.4 收益：契约测试能捕获的缺陷类型，当前门禁是否已覆盖？

| 缺陷类型 | 契约测试能捕获 | 当前门禁能捕获 | 增量收益 |
|----------|---------------|---------------|----------|
| 路由增删未同步文档 | ✅ | ✅（门禁 28） | 无 |
| 状态码变更（如 200→204） | ✅ | ⚠️ 仅 login | 中 |
| 字段重命名（如 `user_id`→`userId`） | ✅ | ❌ | 高 |
| 字段类型变更（如 `int`→`string`） | ✅ | ❌ | 高 |
| 必填字段缺失 | ✅ | ❌ | 高 |
| 响应体结构变更（如数组→对象） | ✅ | ❌ | 高 |
| 请求体字段变更 | ✅ | ❌ | 高 |

**结论**：契约测试对「字段重命名/类型变更/必填缺失/响应体结构变更」有高增量收益，当前门禁未覆盖。但这些缺陷**也可通过加强 OpenAPI schema 校验**（如 schemathesis 对 OpenAPI spec 做参数化测试）捕获，不一定需要 pact。

## 3. Rust 生态 pact 方案调研

### 3.1 pact-consumer-rust / pact-rust

| 维度 | 评估 |
|------|------|
| 维护方 | pact-foundation 社区 |
| 成熟度 | 中低。consumer 端 DSL 可用，但 API 稳定性一般 |
| provider 端验证 | 需搭配 `pact-stub-server` 或 pact broker |
| 跨平台 | Rust 原生，无 C 依赖，但 Windows 支持有报告问题 |
| 适合场景 | consumer 端写契约（本仓库是 provider，不直接适用） |

### 3.2 pactffi（FFI 绑定）

| 维度 | 评估 |
|------|------|
| 维护方 | pact-reference（C 库） |
| 成熟度 | 中。FFI 绑定完整，但引入复杂 |
| 引入成本 | 高。需链接 C 库，跨平台编译麻烦（Windows/Linux/macOS 需分别构建），CI 镜像需预装 |
| 适合场景 | provider 端从 pact broker 拉取契约验证 |

### 3.3 pact-stub-server（CLI）

| 维度 | 评估 |
|------|------|
| 性质 | 独立 CLI 二进制，非 Rust 库 |
| 引入成本 | 中。CI 需下载预编译二进制或从源码构建 |
| 适合场景 | provider 端验证（启动 stub server，验证 provider 响应符合契约） |

### 3.4 替代方案：schemathesis（Python）

| 维度 | 评估 |
|------|------|
| 性质 | Python 工具，对 OpenAPI spec 做参数化测试 |
| 能力 | 自动生成测试用例，验证 provider 响应是否符合 OpenAPI spec（状态码 + content_type + 可选 schema） |
| 引入成本 | 低。CI 加一个 Python step，`pip install schemathesis` + `st run openapi-sz300.json --base-url http://localhost:8080` |
| 适合场景 | **provider 端 schema 校验**，无需 consumer 参与，本仓库可独立做 |
| 局限 | 依赖 OpenAPI spec 的完整度（当前 sz300 response body schema 缺失，需先补全 spec） |

### 3.5 替代方案：openapi-generator + 类型化客户端测试

| 维度 | 评估 |
|------|------|
| 性质 | 根据 OpenAPI spec 生成强类型客户端 SDK，编译期捕获字段变更 |
| 引入成本 | 中。需 codegen 步骤 + 生成代码维护 |
| 适合场景 | consumer 端（前端）捕获契约破坏 |
| 局限 | 不在本仓库范围（consumer 在独立仓库） |

### 3.6 综合评估

| 方案 | 引入成本 | 收益 | 适合本仓库 | 结论 |
|------|----------|------|-----------|------|
| pact-consumer-rust | 中 | 中 | ❌ 本仓库是 provider | 不推荐 |
| pactffi + pact broker | 高 | 高（跨仓库） | ⚠️ 需前端仓库配合 | 暂不引入（跨仓库基础设施未就绪） |
| pact-stub-server | 中 | 中 | ⚠️ 需契约文件来源 | 暂不引入 |
| **schemathesis** | **低** | **高**（provider 端 schema 校验） | ✅ 本仓库可独立做 | **推荐作为替代** |
| openapi-generator | 中 | 高（consumer 端） | ❌ consumer 在独立仓库 | 不在本仓库范围 |

## 4. 明确建议

### 建议：**豁免 pact consumer-driven contract 引入 + 定期复审 + 替代方案加强**

### 4.1 豁免理由

1. **架构错位**：本仓库是 provider，主要 consumer（Vue H5 / Tauri / 小程序 / Android）全部在独立仓库（`docs/adr/0052-前端策略.md:98-99`）。consumer-driven contract 测试的设计理念是「consumer 写契约，provider 验证」，在本仓库内做违背其设计理念。正确做法是前端仓库写 pact 契约 → 发布到 pact broker → 本仓库从 broker 拉取验证，这需要跨仓库基础设施（pact broker），超出本仓库范围。

2. **Rust 生态不成熟**：pact 的 Rust 原生实现（pact-consumer-rust）适合 consumer 端，不适合本仓库（provider）。provider 端验证需 pactffi（FFI，引入成本高）或 pact-stub-server（外部 CLI），CI 复杂度显著增加，收益与成本不匹配。

3. **当前已有部分覆盖**：OpenAPI-路由一致性门禁（`ci.yml:677-686`）覆盖路径清单漂移；`login_contract_test.rs` 覆盖 login 状态码契约；OpenAPI spec 静态契约（`schemas/openapi-sz300.json`）可被第三方工具校验。P2-5 缺陷的「路径清单」层已闭环，缺口在「schema 字段」层。

4. **SDET 复评已定性为「nice-to-have」**：`docs/audit/2026-11-06-SDET复评报告.md:323` 明确「剩余 P2-5 契约测试为『nice-to-have』，不阻塞发布」。

### 4.2 替代方案加强（推荐，但不在本评估任务范围内强制落地）

为弥补 schema 层缺口，**推荐**（非强制）后续引入 **schemathesis** 做 provider 端 OpenAPI schema 参数化测试：

- **前提**：先补全 OpenAPI spec 的 response body schema（当前 `openapi.rs` 仅注册 content_type，未注册响应体字段结构）
- **步骤**：CI 加一个 Python step，`pip install schemathesis` + `st run schemas/openapi-sz300.json --base-url http://localhost:8080`
- **收益**：自动生成测试用例，验证 provider 响应符合 OpenAPI spec，捕获字段重命名/类型变更/必填缺失
- **成本**：低（无需 Rust pact 库，无需跨仓库协同）
- **登记**：若落地，需新开任务，不在本评估范围
