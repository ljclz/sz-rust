## 2. 逐项明细（证据 → 修复 → 等级）

### 0-30.1 商户列名 P0

- **缺陷**：列表 SQL 查询生产表不存在的 `merchant_name`，任何商户列表请求必 500/空集。
- **修复**：`packages/sz-rust-sz300/src/services/merchant_service.rs:90` 改为 `SELECT merchant_id, name AS merchant_name, ...`（列名投影，不是 `SELECT *`）；登录/资料接口同样补齐 `m.name as merchant_name`（`src/services/auth_service.rs:383`、`:429`）。
- **测试失真根因**：历史夹具自造了 `merchant_name` 列，所以缺陷长期不被测试发现 —— 已随 0-30.4 一并消除。
- **等级**：**V**（`cargo check -p sz-rust-sz300 --tests` 通过，见 §5 命令 1）。

### 0-30.2 订单号 P0

- **缺陷**：原订单号基于 `UNIX_TIMESTAMP()`（秒级），同秒并发下单必撞 `order_no` UNIQUE。
- **修复**：新增 `packages/sz-rust-sz300/src/services/order_no.rs:17` `generate(device_id)` —— `O` + 13 位毫秒 + 6 位设备号 + 4 位进程内序号 + 3 位抖动 = 27 字符（`order_no VARCHAR(32)` 内）；控制器在请求未带 `order_no` 时调用（`src/controllers/order.rs:164-167`）。
- **兜底**：跨进程唯一性最终仍由 `order.order_no` UNIQUE 保证，冲突时服务层返回「订单号冲突，请重试」而不是写坏数据。
- **等级**：**V**（`services::order_no::tests::test_order_no_unique_in_burst` 在 lib 全量中通过，见 §5 命令 3）。

### 0-30.3 下单事务 P0

### 0-30.7 PG 占位符 / 多方言声明

- **决策**：sz300 **只承诺 MySQL 单主（+ 可选只读副本）**，`docs/database-support-matrix.md` §1 明示全部状态并给出证据列；PG 版 `001_init_pg.sql` 定性为历史草稿（缺 002–007 对等 DDL），不作支持承诺。
- **外部依赖缺陷（本轮实测发现）**：在只读运行上游 `../sz-orm` 的单测时，`cargo test -p sz-orm-sqlx --lib pg_rewrite` 结果为 **3 passed / 1 failed**：

  ```
  thread 'any::tests::test_pg_rewrite_placeholders_keeps_json_operators' panicked at packages\sz-orm-sqlx\src\any.rs:2386:9:
  assertion `left == right` failed
    left: "SELECT * FROM t WHERE doc $1 'k' AND b = $2"
   right: "SELECT * FROM t WHERE doc ? 'k' AND b = $1"
  ```

  即 jsonb 存在操作符 `doc ? 'k'` 被误当成占位符改写，且导致后续参数编号整体错位。
- **为何不在本仓库修**：上游 `AGENTS.md` ADR-0001 明文「严禁下游项目修改上游 sz-orm / sz-rust 仓库的任何文件」，改动只能走上游 PR。
- **上游 PR 建议补丁**（待上游评审，本仓库不落盘）：`pg_rewrite_placeholders` 的 `'?'` 分支增加"下一个非空白字符为 `'`"时视为操作符的判断 —— 占位符后紧跟字符串字面量不是合法 SQL，而 `doc ? 'k'` 是合法 jsonb 语法。
- **等级**：**V**（本仓声明由文档门禁覆盖；上游缺陷有真实测试输出）。

### 31-60.2 keyset 分页 + 批量插入

- **keyset**：`OrderFilters.before_order_id`（`order_service.rs:40`）；提供游标时 `keyset = true`（:101），列表 SQL 不含 `OFFSET`（:182-194），`WHERE order_id < ?`（:151），本页填满才返回 `next_cursor`（:209）；控制器解析游标 `src/controllers/order.rs:62`。
- **日期边界**：`end_date` 解析为次日 0 点的开区间 `created_at < ?`（:140），避免 `<= 'YYYY-MM-DD'` 漏掉当天订单。
- **批量插入**：见 0-30.3 的 `MAX_ROWS_PER_INSERT` 分块。
- **真库发现的计划退化（已修）**：keyset 分支生成 `WHERE merchant_id=? AND order_id<? ORDER BY order_id DESC LIMIT ?`，
  优化器会选覆盖索引 `idx_merchant_created (merchant_id, created_at)`，然后对整段商户订单 filesort：
  `EXPLAIN ANALYZE` 实测读 1000 行、过滤 800 行、排序后才取 20 行（0.51 ms）；
  显式 `FORCE INDEX (idx_merchant)` 后为覆盖索引反向区间扫描，只读 20 行（0.033 ms），
  且该差距随商户订单量线性放大（两份 EXPLAIN ANALYZE 原文见 §5 命令 16）。
  修复：`order_service.rs` 仅在 `keyset && merchant_id.is_some()` 时使用 `FORCE INDEX (idx_merchant)`
  （纯设备游标不加提示，避免退化成全索引扫描）。
- **等级**：**V**（真库 EXPLAIN ANALYZE + 修复后 `order_idempotency_test`/`service_coverage_test` 全绿）。

- **现象（V）**：停库 ≥20s 且存在并发在途查询后，连接池永久耗尽：不再新建连接、所有 `acquire()` 在

  看门狗重启进程；若把 `/health` 从熔断器剥离，必须同时补上这条自愈链路，否则其他类型的假死
  （如线程池耗尽）仍会留下"Pod 存活但零服务"的状态。

第二轮真库验证中已发现并修复的问题（保留登记，避免回退）：

1. **keyset 深翻页计划退化**（31-60.2）：优化器选覆盖索引后 filesort 1000 行，`FORCE INDEX (idx_merchant)` 后只读 20 行。
2. **Saga 真库失败**（31-60.3）：测试夹具订单号 35 字符 > `VARCHAR(32)`，修复后 4/4 通过。
3. **OTA 控制器 IDOR 校验先于参数分支**：直接调用控制器（绕过 auth 中间件）时 `CurrentUser` 为 `None`，返回 `code=403`；测试已改为显式注入身份，并补"跨商户触发被拒"反例。

第三轮新发现、且**本仓库/上游责任已分开登记**的问题：

1. **上游 `sz-orm` 连接池不可恢复卡死**（61-90.4）：停库 + 并发在途请求被取消后，池槽位永久泄漏
   （`acquire()` 在 CAS +1 与建连 await 之间被取消，回滚分支不执行），只能重启进程。
   本仓库已把探针改为"spawn + 3s 预算"避免自伤，并把挂起变成 3s 内 503；
   **上游已于 2026-10-29 用 `SlotGuard` 修复**（`../sz-orm` 提交 `c72d90a1`，`pool.rs`），待重跑演练验证。
2. **上游 `sz-orm` 把 MySQL `JSON` 列解码为 `Value::Null`**（61-90.2）：本仓库用 `CAST(payload AS CHAR)`
   规避，否则 webhook 会收到空载荷。
3. **运维脚本两处缺陷**（1、2 轮遗留）：`SHOW MASTER STATUS` 多列导致 `.pos` 带空字段；
   `mysqlbinlog --raw -r` 传文件而非目录导致归档文件名重复。
4. **镜像选择**：`mysql:8.0` 不含 `mysqlbinlog`，备份验证必须用 `mysql:8.0-debian`。
