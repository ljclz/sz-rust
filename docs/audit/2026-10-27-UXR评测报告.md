## 4. 可用性任务走查（3 个任务）

### 任务 A：5 分钟内跑起 Hello World
- 步骤：读 README → 复制 quick_start 代码 → `cargo run -p sz-rust-examples --bin quick_start` → 访问 9527。
- 卡点：README 前 70 行分散注意力；代码示例依赖 `sz_rust_examples::build_router()`，用户想改成自己的路由需要理解 axum。
- 结果：**可完成**，预计 3-8 分钟（含首次编译）。✅

### 任务 B：用框架写一个「用户 CRUD」
- 步骤：找路由机制 → 找 ORM 查询 → 找控制器基类 → 写 service。
- 卡点：① 路由是 axum 原生（无 `Route::get()` 门面）；② `thinkphp-api-mapping.md` 的 `Db` 门面没有查询 API，用户需转向 SZ-ORM 的 Repository（Data Mapper）——**与 ThinkPHP Active Record 心智模型完全不同**；③ 验证器默认错误消息是英文且无字段名（见 §5）。
- 结果：**卡点显著**，TP 迁移者会在 ORM 一步放弃。⚠️

### 任务 C：部署并得到一个「管理后台」
- 步骤：docker compose 起服务 → 找 admin UI → 期望图形界面。
- 卡点：docker compose 要求先配 `.env`；admin-ui 只有 REST API；admin_demo 打印后退出；唯一前端 sz-rust-visual 是 Tauri 桌面工作台，不是管理后台。
- 结果：**预期落差最大**，对 P3「张总」画像直接劝退。❌

## 6. 核心痛点清单（按优先级）

### P0（必须修，直接影响用户留存）

- **P0-1：管理后台「产品不存在」——headless 库被包装成 Admin 后台。**
  - 证据：README.md:50 声称「Admin 后台管理插件 7 大模块 21 个 REST API」；但 admin-ui/monitor-panel/codegen-ui 均为纯 Rust 后端库（lib.rs 只有 API 模块），无任何 HTML/JS/Vue 资产；`admin_demo.rs:137-140` 打印后即退出。
  - 影响：对 P3 决策者画像，这是最大的预期落差；「有后台」是中小团队选型的关键理由。
  - 建议：要么补一个最小 Vue 管理台（对接已有 REST API），要么在 README 显著位置标注「当前仅 API，无内置 Web 界面」并给出前端脚手架模板。

- **P0-2：英文文档安全声明过期，且是安全相关的过期。**
  - 证据：`README.en.md:45` 称 WASM 端点 `(public whitelist)`；中文 `README.md:47` 已改为「受 JWT 保护」（P0-1 安全修复后）。
  - 影响：英文用户/安全评审读到的是一份「存在公开未授权 WASM 执行端点」的错误描述，可能直接判负；也伤害项目可信度。
  - 建议：立即同步 README.en.md；建立「中英文档安全声明一致性」门禁（可挂在现有 doc-code-consistency 脚本上）。

### P1（应该修，显著降低上手阻力）

- **P1-1：README 前 70 行是版本合并摘要/变更日志，Hello World 被淹没。**
  - 证据：README.md:9-69 为 v2.0.0/v1.9.0 合并叙事；快速上手在 :73。
  - 建议：把「快速上手」提到特性列表之前；版本合并叙事移入 CHANGELOG 或 docs/。
- **P1-2：「API 对齐 ThinkPHP」承诺在 ORM 上不成立。**
  - 证据：`thinkphp-api-mapping.md:18-23` 的 Db 门面仅 `init(pool)/pool_ref()/is_initialized()`，无 `Db::name()->where()->select()` 等价物；ORM 是 Data Mapper/Repository（orm-facade/lib.rs:64-74）。
  - 影响：TP 迁移者最依赖的就是 fluent ORM；此处是最大心智模型断点。
  - 建议：① 在映射表增加「SZ-ORM Repository 快速上手」链接，给一个 `user->where('status',1)->get()` 的等价示例；② 或在 README 明示「ORM 采用 Data Mapper，非 Active Record」。
- **P1-3：CLI 中英混用 + 未实现命令出现在帮助中。**
  - 证据：cli.rs:50 中文 about、error.rs:17-47 英文错误枚举；cli.rs:363-369 `serve:reload`/`serve:log-level` 打印「暂未实现」。
  - 建议：统一错误消息语言；未实现命令从帮助列表移除或标注 [WIP]。
- **P1-4：13/15 个示例无运行指南。**
  - 证据：README 仅覆盖 quick_start 与 crud_demo；blog/ecommerce/iot/multi_tenant/admin/wasm/bench 等 13 个示例无文档说明。
  - 建议：在 docs/examples.md 给每个示例一行「做什么 + 怎么跑 + 是否需要 DB」。
- **P1-5：验证器默认错误消息对用户不友好。**
  - 证据：infra-facade/src/validate.rs:64 默认回退 PHP 英文「not conform to the rules」，无字段名，除非开发者提供 message 映射；sz300 业务侧未调用验证器（README.md:27）。
  - 建议：默认输出 `{field} 必须满足规则` 风格中文消息；在 sz300 至少一个业务接口接入验证器作示范。

### P2（建议修）

1. **docs/sz-rust-skills使用指南.md 名不副实**：是 AI Skill 触发速查表，不是用户指南；建议拆分为「开发者使用指南」与「AI 协作技能说明」。
2. **docs/api-guide.md 归档后无替代**：文档索引标「已归档，以 quick_start 为准」，但 quick_start 只演示最小服务，API 参考缺失。
3. **docker compose 首次体验有门槛**：docker-compose.yml:12,17 用 `:?必须设置`，bare `docker compose up` 直接失败；建议提供 `docker compose --env-file .env.example up` 的一键命令。
4. **框架错误码未 i18n**：http-facade/error.rs 消息硬编码；sz300 的 i18n 错误链路 feature-gated（v19-i18n 默认关）。

## 9. 真实用户研究方案（供后续执行）

### 9.1 招募标准（共 9-12 人）
- 5-6 位：5 年以上 ThinkPHP/Laravel 经验的 PHP 工程师（有真实 SaaS 业务）
- 3-4 位：1 年以上 Rust + Web 后端经验
- 2 位：技术负责人/小团队决策者（有选型权）

### 9.2 半结构化访谈提纲（60 分钟）
1. 背景：你现在用什么栈？最近一次框架选型因为什么决定？
2. 迁移：如果要把一个 PHP 项目迁移到 Rust，你最担心什么？（学习曲线/生态/招聘/部署）
3. 找路：打开 README，30 秒内告诉我这个框架是干嘛的、你能不能用？（可用性测试式提问）
4. 动手：按 README 跑 Hello World，边说边做（think-aloud），记录卡点。
5. ORM：给你一个「用户列表 + 按状态筛选」需求，你会在哪里找 API？找到后满意吗？
6. 管理端：如果团队需要一个后台管理界面，你希望框架提供到什么程度？你能接受「只有 API」吗？
7. 收尾：什么情况下你会放弃这个框架？

### 9.3 可用性测试任务（每个 5-10 分钟，记录完成率/时间/挫败点）
- T1：跑起 Hello World（预期完成率目标 100%）
- T2：用文档找到「如何定义一个 REST 路由 + 查询数据库」（预期目标：≤5 分钟找到可用示例）
- T3：按文档「部署并打开管理后台」（预期目标：明确告知用户「无内置 Web 界面」也算通过——测试的是信息透明度，而非功能）

### 9.4 测量指标
- 任务完成率 / 平均完成时间 / 求助次数 / 可找到性（第几次导航找到目标文档）
- 情绪标记（think-aloud 中的叹气词、放弃语）
- System Usability Scale (SUS) 问卷（10 题，>68 及格）

## 10. 一句话总结

**如果你是这个产品的 UXR，下一步带着两个问题去见真实用户：①「API 对齐 ThinkPHP」这句话里，ORM 的差异会不会让你当场放弃？」②「没有内置管理后台，你的选型还成立吗？」**——答案决定 sz-rust 是「工程师的自嗨」还是「可迁移的产品」。
