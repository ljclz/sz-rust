> **方案日期**：2026-11-06

> **驱动来源**：[2026-11-06-产品经理复评报告.md](2026-11-06-产品经理复评报告.md) §8「8 个关键产品假设」+ §2「3 个用户画像」

> **产品定位**：Rust Web 框架（对标 TP6/TP8 API）+ AI 辅助迁移工具 + 单一开源版本（ADR-043）+ 服务商业化（技术支持订阅/迁移服务/合规报告/托管）
> **执行约束**：本方案不修改任何代码文件、不提交 git；访谈记录落盘 `docs/audit/PMF访谈记录/`（待建目录）

## 0. 方案总览

本方案通过**外部用户访谈 + 迁移试点**两条路径，系统性验证 sz-rust 的 8 个关键产品假设（A1-A8），重点突破 3 个 P0 假设（A1 目标用户身份 / A2 付费意愿 / A7 编译速度），并在 4 周内产出 PMF 判定报告。

**核心逻辑**：当前 8 个假设均仅创始人自证（29+ 项目），无外部独立证据。PMF（Product-Market Fit）未验证是产品经理复评认定的 P0 缺陷（DB-2026-11-06-10）。本方案通过 3-5 个外部用户访谈 + 1 个创始人自有系统的端到端迁移试点，将假设从「自证」升级为「外部验证」。

**8 个关键产品假设速查**：

| # | 假设 | 当前证据 | 验证方法 | 优先级 |
|---|------|---------|---------|--------|
| A1 | 目标用户是"中小企业技术负责人"（非"任何人"） | 仅创始人自证 | 3-5 个外部用户访谈 | **P0** |
| A2 | TP6 迁移者愿意为"AI 辅助迁移"付费 | 无 | 1-2 个迁移试点 | **P0** |
| A3 | "集成系统 vs 孤立应用"是真实差异化需求 | critical-analysis.md:63-77 论证 | 用户访谈确认"跨应用数据互通"是痛点 | P1 |
| A4 | AI 生成 Rust 代码成功率可接受（>50%） | critical-analysis.md:231：50-60% | 端到端验证：自然语言→AI 生成→编译→运行 | P1 |
| A5 | 22 条铁律是产品卖点（非开发负担） | 无外部反馈 | 用户访谈确认"防幻影交付"影响采购决策 | P1 |
| A6 | 单一开源版本+服务商业化可持续 | ADR-043 决策 | 早期收费试点（迁移服务/技术支持） | P1 |
| A7 | Rust 编译速度可通过预编译+增量缓解 | 无验证 | 原型验证预编译模板+增量编译 | **P0** |
| A8 | 29+ 项目作为 RAG 训练资产能提升 AI 生成行业相关性 | 无验证 | 构建 RAG 知识库原型 | P2 |

## 1. 访谈目标

### 1.1 主目标：验证 8 个关键产品假设

| 目标层级 | 假设 | 验证产出物 |
|---------|------|-----------|
| **P0 必达** | A1 目标用户身份 | ≥3/5 访谈对象自我认同为"中小企业技术负责人"且有 TP6/Laravel 存量系统 |
| **P0 必达** | A2 付费意愿 | ≥2/5 访谈对象明确表示愿意为"AI 辅助迁移"付费（含可接受价格区间） |
| **P0 必达** | A7 编译速度 | 迁移试点实测编译耗时 + 访谈对象对编译速度的可接受阈值 |
| P1 | A3 集成系统差异化 | 访谈对象确认"跨应用数据互通"是否为真实痛点 |
| P1 | A4 AI 生成成功率 | 迁移试点实测 AI 生成代码的编译通过率 |
| P1 | A5 铁律卖点 | 访谈对象对"防幻影交付"是否影响采购决策的明确表态 |
| P1 | A6 商业化可持续 | 访谈对象对"开源+服务"模式的接受度 + 付费项偏好排序 |
| P2 | A8 RAG 行业相关性 | 访谈对象对"行业 RAG 知识库"的价值认知（定性） |

### 1.2 副目标：画像分布与竞品认知

- **画像分布**：识别画像 A/B/C 在访谈样本中的真实分布，校验"画像 A 优先"假设
- **竞品认知**：访谈对象是否知道 axum/actix-web/poem/loco 等 Rust 原生框架，及选择偏好
- **迁移意愿**：访谈对象当前系统迁移到 Rust 的真实意愿强度（Likert 1-5）
- **未预期发现**：访谈中出现的未在 8 假设内的痛点/需求（开放捕获，记入「未预期发现清单」）

### 1.3 非目标（明确排除）

- ❌ 不做市场容量测算（属后续市场调研范畴）
- ❌ 不做定价 A/B 测试（仅收集价格区间意向）
- ❌ 不做产品功能优先级投票（功能优先级由技术评估驱动，非用户投票）
- ❌ 不修改任何代码文件、不提交 git

## 2. 访谈对象招募

### 2.1 招募目标

- **数量**：3-5 个外部用户（5 个为理想样本，3 个为最低可执行样本）
- **画像优先级**：画像 A（中小企业技术负责人）≥3 个 → 画像 B（独立开发者/外包）≤1 个 → 画像 C（企业 IT）≤1 个
- **硬性排除**：创始人本人、已参与 sz-rust 开发的任何人员、sz-rust 仓库 contributor

### 2.2 招募渠道建议（按优先级排序）

| 优先级 | 渠道 | 预期产出 | 触达方式 |
|--------|------|---------|---------|
| 1 | **创始人 29+ 项目客户网络** | 最可能命中画像 A（有 TP6 存量 + 已有信任关系） | 创始人直接私聊邀请，话术见 §2.4 |
| 2 | **TP6/ThinkPHP 用户社区** | 命中画像 A 核心（有 TP6 存量系统） | ThinkPHP 官方论坛/V2EX/掘金发帖，标题"TP6 老系统迁移 Rust 调研访谈（45min，有酬谢）" |
| 3 | **Rust 中文社区** | 命中已对 Rust 有兴趣的技术负责人 | Rust 中文论坛/rustcc/知乎 Rust 话题发帖 |
| 4 | **Laravel 用户群** | 扩大画像 A 池子（Laravel 与 TP6 同源生态） | Laravel China 论坛/微信群 |
| 5 | **外包/接单社区** | 命中画像 B（独立开发者） | 程序员客栈/码市/V2EX「外包」节点 |

### 2.3 筛选标准

**入选标准（全部满足）**：

1. ✅ 当前有 **TP6 或 Laravel 存量系统**在生产环境运行（非纯学习项目）
2. ✅ 在公司/项目中具有**技术决策权**（能决定技术栈选型，非纯执行者）
3. ✅ 愿意提供 **45 分钟**访谈时间
4. ✅ 同意访谈纪要**脱敏后用于产品调研**（签署知情同意，见 §4 问卷尾部）
5. ✅ 非 sz-rust 项目相关人员（硬性排除）

**加分项（非必须，命中即高价值样本）**：

- ➕ 系统规模 ≥3 个业务模块（迁移复杂度真实）
- ➕ 团队规模 3-15 人（中小企业画像典型）
- ➕ 曾尝试过其他框架迁移（有迁移经验对比）
- ➕ 对 AI 辅助开发已有使用经验（Cursor/Copilot/Codeium 等）

**排除标准**：

- ❌ 纯学生/无生产系统（画像不匹配）
- ❌ 仅做前端/无后端技术决策权
- ❌ 已是 Rust 框架核心贡献者（利益冲突）

### 2.4 招募话术模板（可直接复制）

**私聊邀请（创始人 29+ 项目客户）**：

> 你好 [姓名]，我正在做一个产品调研——我们在开发一个对标 TP6 API 的 Rust Web 框架，带 AI 辅助迁移工具，想把 TP6 老系统迁移到 Rust。你之前用 TP6 做的 [某项目] 正好是典型场景，能不能花 45 分钟聊聊你现在维护那个系统的痛点，以及如果有个工具能帮你迁移到 Rust 你会不会感兴趣？访谈有 200 元感谢费。完全用于产品调研，不涉及任何销售。

>
> 现招募 3-5 位访谈对象，条件：
> - 当前有 TP6 或 Laravel 存量系统在生产环境运行

> - 愿意 45 分钟访谈（远程，腾讯会议/飞书）

### 2.5 感谢费标准

- 标准访谈（45 min）：**200 元**（微信红包/转账）

- 迁移试点参与（§5，需提供真实系统代码片段）：**1000 元 + 迁移结果免费共享**

## 3. 访谈大纲（半结构化）

> **访谈形式**：1 对 1 远程访谈，腾讯会议/飞书视频，45 分钟
> **访谈者**：创始人或产品负责人
> **记录方式**：录音（征得同意）+ 纪要手记 + 脱敏整理
> **问题数**：18 个核心问题 + 2 个开放收尾，按 6 个模块组织

### 模块 1：背景信息（5 min，Q1-Q4）

| # | 问题 | 目的 | 记录字段 |
|---|------|------|---------|
| Q1 | 请介绍一下您所在公司/团队的基本情况：公司规模、业务领域、技术团队人数？ | 建立画像基线 | 公司规模 / 行业 / 团队人数 |
| Q2 | 您在团队中的角色是什么？技术选型决策由谁拍板？ | 验证技术决策权（筛选有效性） | 角色 / 决策权 |
| Q3 | 您当前主要的技术栈是什么？后端框架、数据库、部署方式？ | 技术栈基线 | 后端框架 / DB / 部署 |
| Q4 | 您有 TP6 或 Laravel 的存量系统吗？大概多大规模（模块数/代码量/运行年限）？ | 验证入选标准 + 迁移潜力 | 框架 / 模块数 / 运行年限 |

### 模块 2：现状痛点（8 min，Q5-Q7）

| # | 问题 | 目的 | 记录字段 |
|---|------|------|---------|
| Q5 | 您当前维护这套系统最大的痛点是什么？（开放，不引导） | 捕获真实痛点排序 | 痛点 1/2/3 |
| Q6 | 系统维护成本占您团队精力的比例大概多少？排期压力大吗？ | 量化维护负担 | 维护精力占比 / 排期压力 |
| Q7 | 过去 12 个月有没有考虑过技术升级/重构/换框架？卡在哪里？ | 迁移意愿 + 阻力 | 考虑过 / 卡点 |

### 模块 3：假设验证 A1-A3（10 min，Q8-Q11）

| # | 问题 | 验证假设 | 目的 | 记录字段 |
|---|------|---------|------|---------|
| Q8 | 如果有一个工具能帮您把现有 TP6/Laravel 系统迁移到 Rust，您觉得这个事情是谁会关心——是您本人、老板、还是团队里某个人？ | **A1** | 验证"中小企业技术负责人"是决策者 | 关心者身份 |
| Q9 | 您听说过"集成系统"（一个系统包含 CMS+商城+用户中心等多应用，数据互通）这个概念吗？您当前系统是集成的还是多个孤立应用？跨应用数据互通对您是痛点吗？ | **A3** | 验证集成系统差异化需求 | 是否集成 / 数据互通痛点 |
| Q10 | （追问 Q9）如果迁移到 Rust，您希望是一个大集成系统，还是多个独立微服务？ | **A3** | 架构偏好 | 架构偏好 |
| Q11 | 您怎么定义"中小企业技术负责人"这个角色？您觉得自己是吗？ | **A1** | 自我认同验证 | 自我认同 Y/N |

### 模块 4：假设验证 A2/A6 付费意愿（8 min，Q12-Q14）

| # | 问题 | 验证假设 | 目的 | 记录字段 |
|---|------|---------|------|---------|
| Q12 | 如果有个 AI 辅助迁移工具能把您的 TP6 系统迁移到 Rust（自动生成 Rust 代码 + 人工审核），您愿意为这个服务付费吗？能接受的价格区间？ | **A2** | 付费意愿 + 价格区间 | 愿付 Y/N / 价格区间 |
| Q13 | （追问 Q12）如果是按迁移模块数收费 / 按项目一次性收费 / 按年订阅技术支持，您偏好哪种？ | **A6** | 付费模式偏好 | 付费模式偏好 |
| Q14 | 除了迁移服务，以下哪些您愿意付费（排序）：技术支持订阅 / 安全合规报告 / 托管运维 / 培训认证 / 都不愿意 | **A6** | 付费项排序 | 付费项排序 |

### 模块 5：假设验证 A5/A7/A8（8 min，Q15-Q17）

| # | 问题 | 验证假设 | 目的 | 记录字段 |
|---|------|---------|------|---------|
| Q15 | 有个 Rust 框架宣称有"22 条铁律"强制防幻影交付（禁止声称已完成但实际未完成，所有完成声称必须附代码+测试+commit 三样证据）。您觉得这种机制会影响您选型决策吗？是加分项还是觉得太严格是负担？ | **A5** | 铁律卖点验证 | 影响 Y/N / 加分/负担 |
| Q16 | Rust 的编译速度比较慢（中型项目增量编译 30s-2min，全量 5-15min）。您能接受吗？如果有个方案能通过预编译模板+增量编译把首次编译压到 1min 内，您觉得重要吗？ | **A7** | 编译速度容忍度 | 可接受 Y/N / 预编译方案重要性 |
| Q17 | 如果这个 Rust 框架内置了行业知识库（比如电商/SaaS/ERP 各行业的代码模板和最佳实践，基于 29+ 真实项目训练），对您选择它有帮助吗？您所在行业的哪些场景最需要这种行业模板？ | **A8** | RAG 行业相关性 | 有帮助 Y/N / 行业场景 |

### 模块 6：竞品认知 + 开放收尾（6 min，Q18-Q20）

| # | 问题 | 目的 | 记录字段 |
|---|------|------|---------|
| Q18 | 您知道以下 Rust Web 框架吗：axum / actix-web / poem / loco？用过哪个？为什么选/不选？ | 竞品认知 + 选型理由 | 知道哪些 / 用过 / 理由 |
| Q19 | 如果让您给"把 TP6 迁移到 Rust"这件事打一个可能性分（1=绝不会做，5=已经在做），您打几分？为什么？ | 迁移意愿量化 | 评分 1-5 / 理由 |
| Q20 | 最后开放问：关于技术栈升级和 AI 辅助开发，您还有什么想说的？有没有我没问到但您觉得重要的？ | 开放捕获未预期发现 | 开放回答 |

### 访谈者注意事项

1. **不引导**：Q5 痛点问题必须开放问，不能提示"维护成本高吗"等引导性话术
2. **追问技巧**：Q9/Q12/Q15 若回答模糊，追问"能具体说说吗"/"能举个例子吗"
3. **沉默容忍**：开放问题后留 3-5 秒沉默，不要急于填补
4. **A4 不直接问**：AI 生成成功率（A4）不通过访谈验证，通过 §5 迁移试点实测
5. **录音同意**：访谈开始前明确询问"可以录音吗？录音仅用于内部整理，脱敏后销毁"
6. **纪要时效**：访谈结束后 24 小时内整理脱敏纪要，落盘 `docs/audit/PMF访谈记录/访谈-N-<日期>-<脱敏代号>.md`

### 5.2 端到端迁移流程

```
阶段 0：基线记录（1 天）

阶段 2：编译验证（1-2 天）
  ├── 全量编译耗时记录（验证 A7）

阶段 3：运行验证（2-3 天）
  ├── Rust 版本启动 + 接口可访问
  ├── 功能等价性测试：TP6 接口 vs Rust 接口，相同输入相同输出
  └── 性能对比：Rust vs TP6（响应时间/吞吐/资源占用）

阶段 4：迁移报告（1 天）
  ├── 迁移成功率 = 成功迁移模块数 / 总模块数
  ├── AI 生成成功率 = AI 生成可直接编译的代码量 / AI 生成总代码量
  ├── 功能等价率 = 通过等价测试的接口数 / 总接口数
  ├── 性能对比表
  └── 痛点记录（迁移过程中遇到的真实问题）
```

## 8. PMF 判定标准

### 8.1 三级判定

| 级别 | 判定条件 | 后续动作 |
|------|---------|---------|
| **强 PMF** | ✅ ≥3/5 访谈对象确认痛点（Q5 提及维护成本/排期/升级意愿）<br>✅ ≥2/5 愿意付费试用（Q19 ≥4）<br>✅ 迁移试点成功率 >50%<br>✅ A1 验证通过（目标用户身份确认） | 启动正式产品化：完善 AI 辅助迁移工具 → 发布 v2.1 → 启动早期收费试点 → 扩大访谈到 10-15 个用户 |
| **弱 PMF** | ✅ ≥2/5 访谈对象确认痛点<br>✅ ≥1/5 愿意付费试用<br>✅ 迁移试点成功率 >30%<br>⚠️ 部分 P0 假设未完全验证 | 针对未验证假设补充验证 → 调整产品定位（如画像 B 提升优先级）→ 再做一轮 3-5 个访谈 → 重新判定 |
| **无 PMF** | ❌ <2/5 访谈对象确认痛点<br>❌ 或 <1/5 愿意付费试用<br>❌ 或迁移试点成功率 <30% | **需重新评估产品方向**：考虑 (a) 调整目标用户画像 (b) 调整核心卖点（AI 辅助迁移 → 其他） (c) 调整商业化模式 → 重新设计假设 → 重新访谈 |

### 8.2 假设级判定（每个假设独立判定）

| 假设 | 验证通过 | 验证失败 | 影响范围 |
|------|---------|---------|---------|
| A1 | 自我认同 ≥3/5 | <3/5 | 产品定位 + 画像优先级 |
| A2 | 愿付费 ≥2/5 + 试点成功 | <2/5 或试点失败 | 商业化可行性 |
| A3 | 数据互通痛点 ≥3/5 | <3/5 | 差异化卖点 |
| A4 | AI 通过率 >50% | <30% | AI 辅助迁移核心价值 |
| A5 | 铁律加分 ≥3/5 | 多数认为负担 | 对外叙事策略 |
| A6 | 愿付费服务 ≥2/5 | <2/5 | 商业化模式 |
| A7 | 编译可接受 OR 预编译重要 | 不可接受且无方案 | 技术风险 |
| A8 | 行业知识库有帮助 ≥3/5 | <3/5 | RAG 优先级 |
