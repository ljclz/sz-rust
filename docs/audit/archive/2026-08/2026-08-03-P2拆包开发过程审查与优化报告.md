### 1.3 根因分析

1. **迭代式开发的规范疲劳**：拆包分 6 个阶段逐步进行，每阶段聚焦编译修复，规范步骤被延后，最终遗忘
2. **Skill 触发机制缺失**：拆包是跨模块的架构变更，没有单一 Skill 覆盖，导致规则 11 被跳过
3. **ADR-017 更新被忽视**：每提取一个 facade 都应更新 ADR-017 的"已提取 Facade"表格，但实际只在开始时写了一版
4. **五维审查认知偏差**：误认为"cargo test 全通过 = 审查通过"，忽略了五维审查是独立于测试的文档化审查流程

## 二、当前劣势分析

### 2.1 架构层面

#### 2.1.1 Facade 依赖方向混乱

```
sz-rust-state-facade → sz-rust-orm-facade (Cache)
sz-rust-cache-facade → sz-rust-orm-facade (Cache)
sz-rust-infra-facade → sz-orm-storage (直接！)
sz-rust-auth-facade   → (无 orm 依赖)
```

**问题**：`sz-rust-infra-facade` 直接依赖 `sz-orm-storage` 而非通过 `sz-rust-orm-facade` 间接依赖，破坏了 facade 层级的一致性。state/cache facade 走 orm-facade，infra-facade 走直接依赖，依赖路径不统一。

**证据**：
- `packages/sz-rust-cache-facade/Cargo.toml`: `sz-rust-orm-facade = { workspace = true }`
- `packages/sz-rust-infra-facade/Cargo.toml`: `sz-orm-storage = { workspace = true }`（直接依赖）

> **2026-08-03 已修复**：`infra-facade/src/upload/storage.rs` 中所有 `sz_orm_storage::` 引用已改为 `sz_rust_orm_facade::`，`Cargo.toml` 中 `sz-orm-storage` 依赖已替换为 `sz-rust-orm-facade`。依赖方向现已统一。

#### 2.1.2 循环依赖风险

`sz-rust-core` re-export 所有 facade，facade 之间也存在交叉依赖（state→orm，cache→orm）。当前无循环，但未来新增 facade 时容易引入循环依赖，缺少架构守护机制（如 `cargo deny` 或 `cargo udeps`）。

#### 2.1.3 剩余模块耦合严重（P3 已全部解耦）

sz-rust-core 原剩余 25,101 LOC 中，以下模块曾因强耦合无法提取：

| 模块 | 阻塞原因 | 耦合对象 | P3 提取结果 |
|------|---------|---------|------------|
| `view` | 调用 `respond_html` + DI 容器 + cache | http-facade + state-facade + container | ✅ sz-rust-mvc-facade |
| `controller` | 依赖 request/response/validate | http-facade + infra-facade | ✅ sz-rust-mvc-facade |
| `guard` | 依赖 middleware::auth + error | 未提取的 middleware + http-facade | ✅ sz-rust-mvc-facade |
| `hooks` | 直接依赖 sz-orm-core | orm 层 | ✅ sz-rust-orm-ext-facade |
| `model` | 直接依赖 sz-orm-core | orm 层 | ✅ sz-rust-orm-ext-facade |
| `routing` | 依赖 router + guard + middleware | 多个未提取模块 | ✅ sz-rust-router-facade |

> **2026-08-03 P3 完成**：6 个阻塞模块 + middleware 簇（14 个中间件 + log）+ router/websocket_route/openapi
> 已按依赖簇提取为 4 个新 facade（orm-ext / router / middleware / mvc，合计 ~34.6K LOC），
> 详见 ADR-019。sz-rust-core 由 57K LOC 降至 ~9.2K（−83.9%），"剩余模块占 ~60%"问题清零。

### 2.3 代码质量层面

#### 2.3.1 提取过程中的 sed 副作用

拆包过程中使用了大量 `sed -i` 批量替换（如 `crate::` → `sz_rust_orm_facade::`），导致：
- `event.rs` 的 `facade` 子模块中 `use crate::*` 应改为 `use super::*`（已修复）
- `memcached.rs` 测试中 `use super::*` 被误改为 `use crate::*`（已修复）
- infra-facade 4 个文件的测试 `use crate::*` 应改为 `use super::*`（已修复）
- auth-facade 3 个文件的测试同样问题（已修复）

**风险**：sed 批量操作可能还有遗漏的副作用，当前仅修复了编译报错的部分，语义层面的错误（如逻辑变更）无法通过编译发现。

> **2026-08-03 sed 副作用专项审计结论**（4 项检查全部通过）：
>
> | 检查项 | 方法 | 结论 |
> |--------|------|------|
> | Check 1：facade crate 残留 `crate::` 引用 | `grep -rn "use crate::" packages/sz-rust-*-facade/src/` | ✅ 全部合法，指向同 crate 内部项 |
> | Check 2：`sz_rust_core::` 残留 | `grep -rn "sz_rust_core::" packages/` | ✅ 全部为 addons 中有意保留的向后兼容路径 |
> | Check 3：`sz_orm_core::` 残留 | `grep -rn "sz_orm_core::" packages/` | ✅ 全部为文档注释，无实际引用 |
> | Check 4：路径遍历防护审计 | 人工审查 `static_files.rs` + `upload/storage.rs` | ✅ `is_path_safe()` 在 serve 前调用；`delete()` 拒绝 `..` 和绝对路径；`upload_by_internal/external` 的 file_name 由 `build_save_name` 生成（格式 `storage/{Ymd}/{YmdHis}{md5[0..5]}{rand}.{ext}`），不接收用户输入 |
>
> **最终验证**：`cargo clippy --workspace --all-targets -- -D warnings` 通过（0 warnings）；`cargo test --workspace --lib` → 4,470 tests passed, 0 failed。

#### 2.3.2 重复代码

### 7.2 核心教训

1. **迭代开发不能成为跳过规范的理由**：拆包分阶段进行是合理的，但每阶段完成后应立即补全规范步骤（ADR 更新、五维审查），而非累积到最后
2. **sed 批量操作是双刃剑**：效率高但风险大，应在每次 sed 后运行 `git diff` 人工审查，而非仅依赖编译通过
3. **cargo test 通过 ≠ 审查通过**：测试验证功能正确性，五维审查验证架构/安全/性能/可读性/正确性，两者不可替代
4. **facade 模式需要配套的依赖治理**：引入 `cargo deny` / `cargo udeps` / `cargo hakari` 是 facade 拆包的必要配套措施
