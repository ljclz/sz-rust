## 一、安全审计（Security Audit）

### 1.1 🔴 P0-SEC-01：MerchantUser 密码字段无脱敏（密码明文泄漏风险）

**文件：** `packages/sz-rust-sz300/src/models/merchant_user.rs:30`

```rust
#[derive(Debug, Clone, Serialize, Deserialize, Model)]
pub struct MerchantUser {
    pub user_id: i64,
    pub merchant_id: i64,
    pub username: String,
    pub password: String,   // ← 无 #[serde(skip_serializing)]
    pub realname: Option<String>,
    ...
}
```

**问题：** `password` 字段直接暴露 `pub` 且无 `#[serde(skip_serializing)]`。任何将 `MerchantUser` 序列化为 JSON 的 API 端点都会将 bcrypt 哈希密码包含在响应体中。

**影响：**
- 攻击者可通过任意返回 `MerchantUser` 对象的 API 获取密码哈希
- bcrypt 哈希虽然抗暴力破解，但泄漏哈希值本身违反安全最佳实践
- 若未来密码算法降级或哈希被彩虹表破解，后果严重

**对比：** `packages/sz-rust-core/src/session.rs` 中的 `SessionData` 正确使用了 `#[serde(skip_serializing)]` 脱敏。但 sz300 所有 model（merchant_user, merchant, product, order, device 等）**均未使用 skip_serializing**。

**报告状态：** 报告声称"敏感字段自动脱敏（`#[serde(skip_serializing)]`）"——**与实际代码不符**。

**修复建议：**
```rust
#[serde(skip_serializing)]
pub password: String,
```

### 1.2 🔴 P0-SEC-02：JWT 密钥空字符串回退（认证绕过风险）

**文件：** `packages/sz-rust-core/src/controller.rs:75-78`

```rust
static JWT_CONFIG: Lazy<JwtConfig> = Lazy::new(|| JwtConfig {
    secret: std::env::var("SZ_JWT_SECRET").unwrap_or_default(),  // ← 空字符串回退
    issuer: std::env::var("SZ_JWT_ISSUER").unwrap_or_default(),
});
```

**问题：** 当 `SZ_JWT_SECRET` 环境变量未设置时，`secret` 回退为**空字符串**而非 panic。这意味着：
1. JWT 签名验证使用空密钥，攻击者可自行伪造任意 token
2. 与 `AuthConfig`（`config/mod.rs`）中 `missing_key => panic!("SZ_JWT_SECRET is required")` 的行为**不一致**——同一项目两套 JWT 配置，一套 panic 一套静默降级

**影响：** 生产环境若部署时遗漏 `SZ_JWT_SECRET`，JWT 认证形同虚设，所有受保护端点可被未授权访问。

**报告状态：** 报告未提及此不一致性。

**修复建议：** 统一为 panic 行为，或至少记录 ERROR 级别日志并拒绝启动。

### 1.3 🔴 P0-SEC-03：Cache::remember 阻塞 tokio worker（拒绝服务风险）

**文件：** `packages/sz-rust-core/src/cache.rs:1185`

```rust
// Cache::remember() 内部
std::thread::sleep(self.remember_lock_poll_interval);  // ← 阻塞 tokio worker
```

**问题：** `Cache::remember` 是同步方法，在高并发场景下被频繁调用。当缓存锁被持有时，该方法使用 `std::thread::sleep` 轮询等待，**直接阻塞 tokio worker 线程**。代码自身文档注释（line 1148）已明确警告此问题但未修复。

**影响：** 高并发下 tokio worker 线程被大量阻塞，导致请求处理线程饥饿，引发拒绝服务。

**报告状态：** 报告声称"无阻塞调用"——**与实际代码不符**。

### 1.7 🔴 P0-SEC-07：Sanctum Token 使用非密码学安全 PRNG

**文件：** `packages/sz-rust-core/src/middleware/sanctum.rs:578-613`

```rust
fn generate_random_hex() -> Result<String, String> {
    // 自定义 xorshift64+ PRNG，种子 = SystemTime + thread_id hash
    thread_local! {
        static SEED: Cell<u64> = Cell::new({
            let now = SystemTime::now().duration_since(UNIX_EPOCH)...as_nanos() as u64;
            let tid_hash = format!("{:?}", thread_id).bytes().fold(0u64, ...);
            now ^ tid_hash
        });
    }
    // xorshift64+ fill...
}
```

**问题：** Sanctum 个人访问令牌使用自定义 xorshift64+ PRNG，以 `SystemTime` + 线程 ID 哈希作为种子。**这不是密码学安全的随机数生成器**。攻击者若能近似系统时间和线程 ID，可预测令牌随机部分，实现令牌伪造。

**影响：** 个人访问令牌（用于 API 认证）可被预测，导致未授权访问。

**报告状态：** 报告未提及。SECURITY.md 声称"密钥从环境变量读取，不硬编码"——**与此矛盾**（测试构建中硬编码了 "shengzhuang"）。

### 1.8 🔴 P0-SEC-08：CSRF Cookie 缺少 Secure 标志

**文件：** `packages/sz-rust-sz300/src/controllers/auth.rs:23-31`


**影响：** CSRF token 可通过 HTTP 被截获，导致 CSRF 防护被绕过。

### 3.3 DI 容器实现

**报告声称：** "Singleton/Transient/Scoped 三种生命周期，RwLock 持锁不跨 await"

**实际验证：** ⚠️ **部分准确，存在重大缺口**。

**3.3.1 RwLock 持锁不跨 await：✅ 正确**
`container/mod.rs:390-394`：
```rust
let guard = self.bindings.read();
let binding = guard.get(&type_id)?.clone();
drop(guard); // 释放读锁后再调用工厂
let instance = (binding.factory)();
```
正确地在调用工厂前释放读锁，避免持锁跨调用。

**3.3.2 ❌ P1-ARCH-DI-01：无循环依赖检测**

**问题：** DI 容器**没有**循环依赖检测机制。`make()` 方法不跟踪解析栈，不检测循环。若服务 A 的工厂尝试 `make::<B>()` 且 B 的工厂尝试 `make::<A>()`，将导致：
- **RwLock 重入死锁**（同一线程再次获取写锁）
- 或**栈溢出**

全局搜索 `circular`、`cycle`、`detect.*depend`、`topological`、`dfs` — **零匹配**。

**影响：** 开发过程中若意外引入循环依赖，将在运行时静默死锁，无友好错误提示。

**3.3.3 ❌ P1-ARCH-DI-02：Scoped 生命周期未集成到请求生命周期**

**问题：** `Scoped` 生命周期（`make_with_scope`/`clear_scope`）已实现且有测试覆盖，但**整个代码库中无任何中间件、路由或服务器代码调用这些方法**。即：
- 无请求上下文中间件生成 `ScopeId`
- 无请求结束时的 `clear_scope()` 调用
- `Scoped` 生命周期在生产中**功能等同于 `Transient`**

**影响：** Scoped 生命周期是死代码，若开发者误以为请求作用域隔离已生效，可能导致数据泄漏。

**3.3.4 ℹ️ DI 是类型映射 + 手动工厂，非自动依赖解析**

DI 容器使用 `TypeId` 作为键，工厂为 `Fn() -> Box<dyn Any + Send + Sync>`。**无自动依赖图解析**，无构造函数参数注入——调用方必须手动解析依赖并传入工厂。`bind_contextual` 存在但需手动注册 `(Consumer, Need)` 对。

### 3.4 🟡 P1-ARCH-01：controller.rs 与 AuthConfig JWT 配置不一致

**文件：** `controller.rs:75-78` vs `config/mod.rs`

**问题：** 同一项目存在两套 JWT 配置机制：
- `controller.rs::JWT_CONFIG`：`unwrap_or_default()` → 空字符串静默回退
- `config/mod.rs::AuthConfig`：`missing_key => panic!` → 启动失败

两套配置独立初始化，可能导致运行时行为不一致。

## 十、结论

**sz-rust 项目状态报告严重虚高，存在系统性漏报问题。**

报告声称的"95.4 分、Level 4、0 P0/P1"与实际代码能力存在显著差距。经 6 个并行审计 Agent + 全局代码扫描 + 逐文件深度审查，发现：

### 核心问题（按影响排序）

1. **🔴 密码学安全缺陷（2 个 P0）**
   - Sanctum 令牌使用非密码学安全的 xorshift64+ PRNG，令牌可被预测伪造
   - CSRF cookie 缺少 Secure 标志，MITM 可截获 CSRF token

2. **🔴 敏感数据泄漏（1 个 P0）**
   - sz300 所有 model 的密码等敏感字段未脱敏，可直接通过 API 泄漏

3. **🔴 认证绕过风险（1 个 P0）**
   - JWT 密钥未设置时静默回退为空字符串，认证形同虚设

4. **🔴 运行时死锁风险（1 个 P0）**
   - DI 容器无循环依赖检测，循环依赖时静默死锁

5. **🔴 阻塞调用未治理（3 个 P0）**
   - Cache::remember、Session store、6 处支付服务均阻塞 tokio worker
   - 与报告"无阻塞调用"声明完全矛盾

6. **🟡 架构缺口（2 个 P1）**
   - Scoped 生命周期未集成到请求生命周期（死代码）
   - ORM facade 未被 core 自身 dogfood（14 处绕过）

7. **🟡 测试覆盖缺口（3 个 P1）**
   - 23 个 otlp 测试默认不运行
   - 9 个 DB 集成测试（含 SQL 注入防护）全部 ignore
   - 31 个公共函数无测试覆盖

8. **🟢 已验证的强项**
   - 参数化 SQL 查询：零 SQL 注入风险 ✅
   - 生产代码零 unwrap：✅
   - 零 unsafe 代码块：✅
   - sz300 分层架构严格：✅
   - bcrypt 密码哈希 + spawn_blocking：✅
   - 11 个 CI 硬门禁（无 continue-on-error）：✅
   - K8s 完整性（HPA/PDB/NetworkPolicy/securityContext）：✅
   - 测试数量实际为 4814（超过报告声称的 4206+）：✅
