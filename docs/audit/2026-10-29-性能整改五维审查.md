**结论：✅ 通过（2 项 ⚠️ 观察项，无阻断）**

| 服务二进制可编译 | `cargo check -p sz-rust-sz300 --bin sz300-server` → `Finished dev profile ... 0 error` |
| 限流桶表有界性 | `TokenBucket::acquire` 先按 `full_refill` 回收空闲桶、再落共享兜底桶（[rate_limit.rs:524](file:///D:/www/test/鲜视达/rust/sz-rust/packages/sz-rust-middleware-facade/src/rate_limit.rs#L524)），新增 `test_token_bucket_max_keys_falls_back_to_overflow_bucket` / `test_token_bucket_reclaims_idle_buckets_before_overflow` 覆盖 |

| 熔断窗口语义保持 | `ErrorWindow::snapshot` 只累计 epoch 落在最近 60 桶内的记录（[circuit_breaker.rs:142](file:///D:/www/test/鲜视达/rust/sz-rust/packages/sz-rust-middleware-facade/src/circuit_breaker.rs#L142)）；新增 `test_stat_window_expires_old_records` / `test_many_records_stay_closed_with_low_error_rate`（10 万条记录、1% 错误率保持 Closed） |
| 门禁判定逻辑 | 回环桩服务三组实测：稳定 → exit 0；注入 20 ms 延迟 → exit 1（QPS −76.33%、P99 +234.87%）；每 50 请求 1 次 500 → exit 1 且**仅错误率**触发（2.255% > 0.5%） |

⚠️ 观察项：
1. 桶表溢出时所有新 key 共享同一兜底桶 —— 超载下会相互挤占配额。这是刻意的"有界内存优先"取舍，
   已在 ADR-046 决策 1 记录；`max_keys` 默认 10k，单桶配额在满表场景下降属于预期降级。
2. CI 数据集 `deploy/sql/perf-seed.sql` 与 workflow 的 migrations 应用顺序**未在本机实际执行**
   （需要一次性 MySQL 实例，本次未启动）→ 见本报告"未验证项"。

## 维度 3：架构

**结论：✅ 通过（1 项 ⚠️）**

| 检查点 | 证据 |
|---|---|
| 复杂度下界 | 熔断记录从 O(n) `retain` 降为 O(1) 写入（[circuit_breaker.rs:120](file:///D:/www/test/鲜视达/rust/sz-rust/packages/sz-rust-middleware-facade/src/circuit_breaker.rs#L120)），失败时仅固定 60 槽扫描 |
| 分层未破坏 | 限流/熔断仍在 middleware-facade，sz300 只做接线（`main.rs` 的 `into_make_service_with_connect_info`）与配置映射 |
| 配置外置 | 池探活、限流容量、熔断窗口全部走环境变量，无硬编码常量替换 |
| 门禁与 CI 解耦 | 脚本零依赖（只用 node 内置 `http/crypto/os`），本地与 CI 同一入口；基线按指纹分槽，不共享机器 |
| 可回退 | 五项变更互相独立，均可单独 revert；门禁 v2 与 workflow 不改变运行时行为 |

⚠️ 观察项：默认 60 s 窗口下桶粒度为 1 s，`stat_window` 若被配置为 < 60 s，粒度会等比缩小
（`window / 60`），极端配置（如 1 ms）下桶会被高频重置。已在 `ErrorWindow::new` 用 `.max(1)` 兜底
（[circuit_breaker.rs:108](file:///D:/www/test/鲜视达/rust/sz-rust/packages/sz-rust-middleware-facade/src/circuit_breaker.rs#L108)），
但未对"窗口 < 1 s"做语义保证。

## 维度 4：安全性

**结论：✅ 通过（1 项 ⚠️ 遗留，非本次引入）**

| 检查点 | 证据 |
|---|---|
| 限流失效路径消除 | 旧版 `max_keys` 溢出返回 `Err` → 中间件 fail-open → 限流完全失效；新版改为回收 + 兜底桶，**不存在拒绝即放行的路径** |
| 代理头不再无条件信任 | 仅 `trust_proxy=true` 解析 `X-Forwarded-For` / `X-Real-IP`，且必须 `parse::<IpAddr>()` 成功（[rate_limit.rs:242](file:///D:/www/test/鲜视达/rust/sz-rust/packages/sz-rust-middleware-facade/src/rate_limit.rs#L242)）；新增 `test_extract_client_ip_untrusted_ignores_proxy_headers` / `test_extract_client_ip_trusted_proxy_invalid_header_falls_back` |
| 键空间不可污染 | 非 IP 头值直接忽略并回落到对端 IP，垃圾头无法制造无限 key |
| 门禁不对共享环境施压 | 默认仅允许回环地址，远端需显式 `--allow-non-loopback`（实测 `--host 10.0.0.5` → exit 2 拒绝） |
| CI 凭据 | workflow 只用 service 内一次性密码（`test123`）与自签 JWT 密钥，无仓库 secret 依赖 |
| 日志降级不泄露 | 降为 `debug!` 的是读路径计数/成功信息，不含凭据字段；写路径审计日志保持 `info!` |

⚠️ 遗留（**本次未修，需下一轮处理**）：`ip_access_control.rs:228-243` 在信任校验**之前**就用
`x-real-ip` / `x-forwarded-for` 构造 `peer_addr`，与本次修复的限流同类问题（可由客户端伪造来源 IP）。
影响面为 IP 黑白名单中间件，不在 0–30 天路线范围内；建议按本次 `peer_ip` 方案统一改造。

**仍未验证清单**（不得在后续文档中当作已验证结论）：
1. 限流从单桶改为按 IP 分桶后，业务可用吞吐 1.13k → 2.1k 的复测（需与修复前同源 DB + 数据集 + 空闲机）；
2. ~~熔断 O(1) 窗口在 `/health` 上的稳态收益~~ → **已实测 +34.9%（下界），达成值受单压测进程天花板 6.2–6.9k 约束**；多进程/压测机分离后的真实上限仍未测；
3. `test_before_acquire=false` 对 product/order 列表 p99 的单独影响；
4. CI 侧 migrations 001–007 + `perf-seed.sql` + sz300 启动 —— **本机已全部实跑通过**（含 seed 首跑暴露的 `market_id` 缺列并修正），但 GitHub runner 上的 `perf-gate.yml` 实跑与 `--init` 播种仍未验证；
5. 审计落库超时的根因占比（DB 慢 vs 池等待 vs 锁），以及其**发生频率分布**（两轮实测 397 / 0 条，单轮计数不足以定阈值）；
6. 第二轮 `/health` 相对第一轮 +6.1%（5886.8 → 6248.7）的差因——本轮未挂处理器负载采样，无法归因。

## 合入结论

- 正确性 ✅ / 可读性 ✅ / 架构 ✅ / 安全性 ✅ / 性能 ⚠️
- **无 ❌ 阻断项**；性能维度的 ⚠️ 已收敛为「`/health` 两轮 release 独立实测 +34.9%（下界）~ +43.2%；业务端点**同源 A/B 已做**（product +5.2% / order +8.6%，W 级，无回归但受同机争用干扰），V 级量值待空闲机/压测机分离」。
- 真库端到端链路已实跑通三轮（migrations + seed + release 服务 + 门禁，三端点 0% 错误），
  剩余缺口是**空闲机/分离压测环境**（31–60 天路线项）而非机制可用性；下一台具备空闲机 + 可复制修复前数据集的机器上跑
  `node scripts/perf-regression.js --init` 提交基线，再复测上述 1/3/5。
- 现场验证暴露的每请求 WARN 已在本审查周期内修复，并有 debug + release 两档前后实测数（记录 §4/§11.4/§12.3）；
  审计丢弃（单轮 0~397 条）为本审查新发现的独立缺陷，未修，需产品/合规决策。
