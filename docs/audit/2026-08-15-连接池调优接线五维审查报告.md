## 一、正确性 ✅

- 两层池容量对齐约束显式化：scaler 扩容上限 = `pool.max_size()`（= SQLx 池 max_connections），下限 = `min_idle`，避免历史缺陷复发（SQLx 默认 10 < sz-orm 20 时第 11 个并发 acquire 超时）。证据：`main.rs:218-223` 注释 + `PoolScalerConfig` 构造。
- 仅当 `adjust()` 实际改变 target 才 `resize()`，避免"启动即缩容"（初始 target=min_connections 与池现状不一致的问题）。证据：`main.rs:243-253`。
- 测试证据：`cargo test -p sz-rust-sz300 -j 2` → lib 43 passed（含新增 4 个 `db::tests`：默认值 / 环境变量覆盖 / 非法值回退 / PG 固定配置），集成测试全部通过（endpoint_coverage 6、metrics_auth_router 7 等）。测试中的 `std::env` 竞争已用 `ENV_LOCK` 互斥串行化（`db.rs:150-154`）。
- 编译证据：`cargo check -p sz-rust-sz300` → Finished 无 error；`cargo clippy -p sz-rust-sz300` → 零警告。

## 二、可读性 ✅

- `db.rs` 配置构造集中为 `mysql_pool_config_from_env()` / `pg_pool_config()` 两个函数，常量（`MYSQL_POOL_MAX` 等）带注释说明与既有默认一致。
- scaler 任务块内注释说明指标映射语义：`acquire_failed_count`（含超时/建连失败/池关闭/限流拒绝）作为超时率代理（`main.rs:236-238`）。
- /metrics 输出函数 `append_pool_metrics(prefix, pool)` 对 MySQL/PG 复用。

## 三、架构 ⚠️

- 接线遵循既有分层：配置读取在 `db.rs`（db 层）、后台任务在 `main.rs`（启动编排）、输出在 controller。facade 零改动（`pool_config.rs` / `pool_scaler.rs` 的 pub API 不变），无新 ADR 义务。
- ⚠️ 已知边界：facade `PoolWarmer`（connect_fn 不返回连接）与 sz-orm Pool（无公开"建连入池"API）接口不匹配，预热走 sz-orm 原生 `prewarm()`（`db.rs:72-74` 注释说明）。`PoolWarmer` 保持为通用组件，未在 sz300 使用——这是接口语义决定的取舍，非遗漏。
- ⚠️ 已知边界：`Pool::resize` 扩容受空闲队列原始容量限制（超出部分 release 时关闭），动态扩容的效果是"突发吸收"而非持久扩容（sz-orm-core 4.7.0 `pool.rs:1739-1747`）。当前区间 [10, 20] 内行为符合预期。

## 四、安全性 ✅

- 池指标经 /metrics 端点输出，该端点已有独立鉴权（Bearer token + IP 白名单，`SZ300_ENV=production` fail-closed，`main.rs:257-273`）——池状态（active/idle/max）不泄露敏感数据，鉴权复用无新增暴露面。
- 环境变量读取全部 `parse().ok()` 回退默认，非法输入不 panic（`db.rs:45-47`）。
- 无新增 unsafe、无敏感字段输出。

## 五、性能 ✅

- /metrics 池指标实时读取：`Pool::status()` / `pool_metrics()` 仅原子计数器（O(1) 无阻塞），不占请求关键路径（`health.rs:117-119` 注释）。
- 预热接线消除首次请求冷启动延迟；SQLx 层 `idle_timeout`/`max_lifetime` 补齐后与 sz-orm 层双保险，防死连接。
- ⚠️ 注意：scaler 任务每 30s 一次 O(1) 读取，开销可忽略；`resize()` 仅原子写（`set_max_size`），无锁竞争。

## 结论

5 个维度均无阻断项（❌ 0 项），本次变更可合入。遗留边界（PoolWarmer 未接线、resize 扩容语义）已在"架构"维度标注为已知取舍。
