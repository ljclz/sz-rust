## 1. 一句话架构判断

**当前阶段应做「减法 + 收口」：生产就绪的硬障碍几乎全部是「已存在问题未收口」（插件伪验签、英文文档安全声明过期、sz300 无覆盖率门禁），而不是「缺新功能」。过去一天团队已快速修复 SDET/AppSec 报告的 6+ 项 P0/P1，证明「先修问题」的 ROI 远高于「再加功能」。**

## 4. 「下一步方向」建议：先收口，再谈新方向

**明确回答用户的问题：下一步应该「解决存在的问题」，而不是「规划新功能」。** 理由：

1. **生产就绪的阻塞项全部是问题而非缺功能**：插件伪验签是安全漏洞级缺陷，英文文档安全声明过期会直接误导用户/安全评审，sz300 无覆盖率门禁意味着主业务应用的回归防护是盲区。
2. **修复 ROI 极高**：过去一天已修复 10+ 项 P0/P1，证明收口的边际成本远低于新增功能（新增功能还会引入新的测试/文档/安全义务）。
3. **新方向的先决条件未满足**：插件市场（验签是假的）、管理前端（仍是 headless 决策未定）、ORM 对齐（承诺与实现不符）——这三个「新方向」的底座都是坏的，必须先修。

**唯一值得现在启动的「新方向」是决策型任务**（不是写代码）：
- 前端策略 A/B 决策（真建 Vue 管理台 vs 永久 headless）
- ORM 策略决策（补 ThinkPHP 流畅 facade vs 正式声明 Data Mapper 并给迁移示例）
- 部署形态决策（TLS 终止归 nginx/宝塔模板 vs 进程内 TLS）

## 5.5 重要补充：数据层是当前最大生产就绪阻塞（2026-10-28 新审计）

> 本报告撰写期间，并行会话发布了 `docs/audit/2026-10-28-数据库层独立审计报告.md`（本报告未独立复跑其结论，以下转述其要点，**建议将其纳入本路线图的最高优先级**）。

- **数据层评分 40/100（D 级，不可承载生产数据）**，三条硬阻断：
  1. 商户列表查询 `merchant_name`，生产 DDL `001_init.sql` 中列名为 `name` → 生产必报 `Unknown column`（merchant_service.rs:88）。
  2. 订单号用 `CONCAT('O', UNIX_TIMESTAMP())` 生成（mqtt_service.rs:158）→ 同秒多单必撞 `UNIQUE(order_no)`。
  3. 下单头+行无事务、行插入失败被 `tracing::error!` 吞掉；sz300 全目录 `begin_transaction|commit|rollback` 命中数 = **0**（order_service.rs:226-268）。
- 其他：测试 Schema 与生产 DDL 不同源、PG 迁移 `?` 占位符必败、Saga/TCC 不落库且 TCC 空回滚、0 FK / 0 CHECK。

**架构判断修正**：框架层（Phase 0-2）的工程化已接近就绪，但 **sz300 业务数据层仍是原型级**。生产就绪路线图的**最高优先级应从「插件验签」上移到「数据层整改」**——框架再安全，业务表查询都会报错、下单会丢数据，就无法上线。

### 数据层整改路线（并入 Phase 0，作为第一优先）

| # | 动作 | 验收标准 |
|---|---|---|
| D1 | 修复 `merchant_name` → `name` 列名不一致（或改 DDL），并加「查询列名 vs 生产 DDL」一致性门禁 | 商户列表在生产 Schema 上查询通过 |
| D2 | 订单号改为数据库自增/雪花/UUID 方案，去除秒级碰撞 | 并发压测同秒多单无冲突 |
| D3 | 下单头+行包进 `begin_transaction/commit/rollback`，失败返回 5xx 而非吞错 | 行插入失败时整单回滚并有测试 |
| D4 | 测试 Schema 与生产 DDL 同源（migration 即真相） | `migrate` 在空库上执行成功 |
| D5 | 修复 PG 迁移占位符（`?` → `$1` 方言） | PG 迁移全绿 |

## 6. 架构级风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| **64 包碎片化** | 新用户认知负荷高、维护成本大 | 保留 facade 分层但明确「聚合包 `sz-rust-facade`」为唯一入口；在 README 画依赖图 |
| **sz-orm 版本漂移**（锁 10.12.0 解 10.13.0） | 传递依赖升级可能导致行为变化 | 用 `[patch.crates-io]` 或 workspace 内 pin；发布前锁定 Cargo.lock |
| **并发会话写冲突**（docs/audit 被多会话同时改） | 文档互相覆盖 | 约定「每个报告一个会话 + 文件头加 `⚠️ 正在编辑` 标记」；或对高冲突文件用 append-only |
| **前端策略悬而未决** | headless 更名只是止血，产品承诺仍模糊 | Phase 1 必须做出 ADR 决策 |
| **AI/WASM ROI 存疑** | 边缘计算与 AI 端点对菜市场 SaaS 场景可能过剩 | 以插件市场真实需求驱动，避免「为技术而技术」 |

## 7. 结论

**如果你是这个项目的 TA，未来 4 周最优先做的三件事：**
1. **整改数据层（40/100 D 级）**：先修三条硬阻断——`merchant_name` 列名、订单号秒级碰撞、下单无事务（详见 §5.5）。这是「能演示」与「能承载生产数据」的分水岭。
2. **修掉插件伪验签**（P0 安全缺陷，1-2 天工作量，`ed25519-dalek` 已在依赖中）。
3. **把 sz300 加进覆盖率矩阵 + 修复 README.en.md 安全声明**（两个「一行改动」，消除主应用覆盖盲区与英文文档误导）。

生产就绪度判定：**框架层基本就绪，但业务数据层（sz300）为 D 级原型，不可承载生产数据**。真正的生产就绪路径是：数据层整改（最高优先）→ 插件验签/文档/覆盖收口 → TLS 部署模板 → 前端与 ORM 决策落地。
