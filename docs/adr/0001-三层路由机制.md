# ADR-001：三层路由机制（属性宏 / 配置式 / 约定式）

> **状态**：已接受
> **日期**：2026-07-22
> **决策者**：SZ-Rust Team
> **关联 ADR**：无
> **相关代码**：`packages/sz-rust-core/src/routing.rs`、`packages/sz-rust-core/src/router.rs`

## 背景

SZ-Rust 对标 ThinkPHP 8，需要提供与 PHP `think-route` 等价的路由能力。PHP 端路由有三种来源：

1. **注解路由**：`#[Route]` 注解（PHP 8 Attribute），控制器内嵌声明
2. **配置式路由**：`config/route.php` 文件，路由与代码解耦
3. **约定式路由**：`auto_multi_app=true` + `app/controller/action` 自动映射

如果只提供一种路由机制，会导致：
- 只提供属性宏路由 → 无法兼容 PHP 配置式路由的迁移
- 只提供配置式路由 → 无法享受编译期类型检查
- 只提供约定式路由 → 生产环境难以维护，路径与代码耦合

此外，PHP 端 `app_map`（oapc/admin/api/farm/oapi/cashier/scene）和 `deny_app_list`（common）是硬约束，必须在路由解析时遵守。

## 决策替代方案

在确定三层路由机制前，曾考虑以下替代方案：

### 方案 A：仅使用属性宏路由（类似 Actix-web）

```rust
#[get("/users/{id}")]
async fn show(id: i64) -> impl Responder { ... }
```

**拒绝原因**：
- 无法兼容 PHP 配置式路由的迁移路径（PHP 端大量使用 `config/route.php`）
- 无法支持运行时动态添加路由（如插件系统）
- 约定式路由的零配置优势无法保留

### 方案 B：仅使用配置式路由（类似 Laravel）

```php
Route::get('/users', 'UserController@show');
```

**拒绝原因**：
- 失去编译期类型检查，路由错误只能在运行时发现
- 无法享受 Rust 宏的类型安全优势
- PHP 迁移时可以逐步迁移到属性宏，但纯配置式无法渐进

### 方案 C：仅使用约定式路由（类似 ThinkPHP 默认）

```
/app/controller/action → 自动映射
```

**拒绝原因**：
- 生产环境难以维护，路径与代码强耦合
- 无法表达复杂路由（如 RESTful 资源路由、组级中间件）
- 安全审计困难（无法静态分析所有路由）

### 最终选择：三层并存，优先级递减

综合以上分析，选择三层并存方案：
- Layer 1（属性宏）：编译期类型安全，优先级最高
- Layer 2（配置式）：迁移兼容，支持运行时动态添加
- Layer 3（约定式）：零配置快速启动，优先级最低

三层独立、可组合使用，冲突时 Layer 1 > Layer 2 > Layer 3。

## 决策

采用**三层路由机制**，三层独立、优先级递减、可组合使用：

### Layer 1 — 属性宏路由（编译期，最高优先级）

```rust
#[controller(prefix = "/users")]
struct UserController;

impl UserController {
    #[get("/{id}")]
    fn show(&self, id: i64) -> String { ... }
}
```

- 由 `#[controller]` + `#[get]`/`#[post]` 等属性宏自动实现 `ControllerRouter` trait
- 编译期检查路径模板语法
- 优先级最高，覆盖 Layer 2/3 的同路径路由

### Layer 2 — 配置式路由（加载期，中等优先级）

```yaml
# config/route.yaml
routes:
  - method: GET
    path: /users
    handler: User@list
groups:
  - prefix: /api/v1
    middleware: [auth, log]
    routes:
      - method: GET
        path: /items
        handler: Item@list
```

- 支持 YAML / JSON 两种格式
- 支持 `RouteGroup`（前缀 + 组级中间件）
- `HandlerRef::parse("Controller@action")` 对齐 PHP `Route::rule('path', 'Controller/action')`
- 严格校验控制器名和 action 名（`[A-Za-z_][A-Za-z0-9_]*`），拒绝 `../`、空格、`@` 等注入字符

### Layer 3 — 约定式路由（运行时，最低优先级）

```
URI: /oapc/customer/index
  → app=oapc, controller=Customer, action=index
  → 自动映射到 Customer 控制器的 index 方法
```

- 基于 `parse_path()` 解析 `(app, controller, action)` 三元组
- 遵守 `APP_MAP` 白名单（oapc/admin/api/farm/oapi/cashier/scene）
- 遵守 `DENY_APP_LIST` 黑名单（common 被当作控制器处理）
- 默认值：`app=index`、`controller=Index`、`action=index`

### 优先级合并规则

```rust
// RouteRegistry::merged_rules()
// 优先级低 → 高（后插入覆盖前插入）
for rule in self.convention_as_rules() { seen.insert(key, rule); }
for rule in &self.config_routes { seen.insert(key, rule); }
for rule in &self.attribute_routes { seen.insert(key, rule); }
```

冲突时 Layer 1 > Layer 2 > Layer 3。

## 后果

### 正面后果

- **PHP 迁移友好**：三种路由方式都与 PHP 对齐，迁移时可选择最合适的方式
- **渐进式迁移**：从 Layer 3 起步（零配置），逐步迁移到 Layer 2（配置化），最终到 Layer 1（类型安全）
- **类型安全**：Layer 1 在编译期检查，Layer 2/3 在加载期检查
- **安全**：`HandlerRef::parse` 严格校验标识符，阻止路径穿越注入
- **冲突可检测**：`RouteRegistry::attribute_conflicts()` / `config_conflicts()` 可在启动时检测同层冲突

### 负面后果

- **复杂度增加**：三层路由比单一路由机制更复杂，需要 `RouteRegistry` 管理合并
- **性能开销**：三层合并需要在启动时遍历所有路由（`O(n)` 一次），但运行时无开销（axum 路由表已构建）
- **Layer 1 属性宏已实现**：`#[controller]` 宏已在 sz-rust-macros 中实现，自动为控制器结构体实现 `SzController` trait

## 注意事项

- **Layer 3 的 `app_map` 是硬编码**：`APP_MAP: LazyLock<HashSet<&'static str>>` 包含 7 个应用名。如果新增应用，需要修改源码。未来可考虑从配置文件加载。
- **`parse_path` 的首字母大写规则**：`capitalize_first("customer") → "Customer"`，但 `capitalize_first("customerList") → "CustomerList"`（仅首字母大写，不强制后续小写）。这与 PHP 的 `parseName` 行为一致。
- **HandlerRef 的分隔符**：优先按 `@` 分隔，其次按 `/` 分隔。PHP 端两种分隔符都支持，Rust 端保持兼容。
- **路径模板语法**：Layer 2 的 `path` 字段使用 axum 0.8 路由语法（`/users/{id}`），而非 PHP 的 `<id>` 语法。迁移时需要转换。

## Bug 定位提示

如果生产 Bug 表现为"请求返回 404"或"路由匹配到错误的 handler"：

1. **L1 决策层**：查阅本 ADR，确认路由是否按预期方式注册（Layer 1/2/3？优先级是否冲突？）
2. **L2 运行时层**：检查 tracing span `route.match` 中的 `matched_path` 和 `handler` 字段
3. **L3 指标层**：检查 `route.match.miss` 指标是否突增
4. **L4 代码层**：
   - 路径解析 Bug → 检查 `packages/sz-rust-core/src/router.rs` 的 `parse_path()`
   - 配置加载 Bug → 检查 `packages/sz-rust-core/src/routing.rs` 的 `load_routes_from_yaml_str()`
   - 优先级合并 Bug → 检查 `RouteRegistry::merged_rules()` 的 `seen.insert` 顺序
   - 注入字符 Bug → 检查 `HandlerRef::parse()` 的 `is_valid_identifier()` 校验
   - **应用不在 APP_MAP** → 新应用名未加入 `APP_MAP` 白名单，约定式路由返回 404（检查 `router.rs` 的 `APP_MAP` 常量）
   - **控制器名大小写异常** → `capitalize_first("customerList")` 仅大写首字母（`CustomerList`），不强制后续小写；若期望 `Customerlist` 会匹配失败
