# ADR-019：P3 剩余模块解耦（四簇提取）

> **状态**：已完成
> **日期**：2026-08-03
> **决策者**：SZ-Rust Team
> **关联 ADR**：ADR-017（sz-rust-core 拆包策略）、ADR-018（facade 独立发布策略）
> **相关代码**：
> - `packages/sz-rust-orm-ext-facade/`（model/hooks/relation）
> - `packages/sz-rust-router-facade/`（router/routing/websocket_route/openapi）
> - `packages/sz-rust-middleware-facade/`（auth/sanctum/jwt_blacklist 等 14 中间件 + log）
> - `packages/sz-rust-mvc-facade/`（view/controller/guard）
> - `packages/sz-rust-core/src/lib.rs`（re-export 切换）

## 背景

ADR-017 拆包后 sz-rust-core 剩余 25,101 LOC 中，view/controller/guard/hooks/model/routing
六个模块因强耦合暂无法提取（审查报告 2.1.3）。P2 审查报告（四评 97.50/100）将解耦列为
P3 迭代目标：

| 模块 | 原阻塞原因 |
|------|-----------|
| `view` | 依赖 `respond_html`（http-facade，已解）+ DI 容器（实测不依赖 Container 类型） |
| `controller` | 依赖 request/response/validate（均已 facade 化） |
| `guard` | 依赖 middleware::auth（本轮随 middleware 簇一起提取） |
| `hooks` / `model` | 直接依赖 sz-orm-core（经 orm-facade 间接依赖，已解） |
| `routing` | 依赖 router + guard + middleware（router 同簇带走） |

## 决策

按**依赖簇**分四批提取为 4 个新 facade crate：

### 簇 1：sz-rust-orm-ext-facade（model + hooks + relation，~10.2K LOC）
- 依赖：仅 sz-rust-orm-facade（Model/ModelExt/Relation 等已覆盖）+ sz-orm-core（dev，供 relation 测试）
- core 内零反向依赖，无环风险，最先提取

### 簇 2：sz-rust-router-facade（router + routing + websocket_route + openapi，~3.9K LOC）
- 依赖：axum/serde/serde_json/serde_yml/thiserror/tokio/tracing
- 簇内互引用（routing→router→websocket_route、openapi→routing），搬移后 `crate::` 路径零修改
- 注：openapi 有下游消费者（sz300），提取后 core re-export 保持兼容

### 簇 3：sz-rust-middleware-facade（14 个中间件 + log 门面，~9.9K LOC）
- **环解法**：原 `container ↔ request_scope` 双向耦合（`container::ScopeId` 类型 +
  `request_scope::current_scope_id()` 状态）。将 `ScopeId` 定义迁移至 middleware-facade 顶层，
  core 的 `container` 改为 `pub use sz_rust_middleware_facade::ScopeId` 重导出——
  依赖方向变为单向 `core(container) → middleware-facade`，环消除
- 安全关键文件（auth/jwt_blacklist/sanctum）**保留 `@REVIEW_REQUIRED` 标记**，纯搬移零逻辑改动
- 两个 log 文件合并：`log.rs`（LogFacade 门面）+ `middleware/log.rs`（LogConfig/中间件）→
  facade 内单一 `log.rs`，下游 `sz_rust_core::log::LogFacade` 与 `sz_rust_core::middleware::log` 均保留

### 簇 4：sz-rust-mvc-facade（view + controller + guard，~10.6K LOC）
- 依赖：http-facade（request/response/error）+ infra-facade（validate）+ middleware-facade（auth）
  + orm-facade（controller 的 JWT 校验，原直接引用 sz_orm_auth 已改为走 facade）
- guard 依赖 middleware-facade 的 auth，必须排在簇 3 之后

### 统一兼容策略
- 所有新 facade 在 core 中以 `pub use <facade> as <module>` / `pub use <facade>::<module>` 重导出，
  下游 `sz_rust_core::<module>::*` 路径零改动
- `#[controller]` 宏硬编码 `::sz_rust_core::controller::SzController`：core 保留 controller
  re-export，宏零修改（facade 模式的红利）
- 提取后 core 剩余 10 个源模块（addons/api_version/cache_warmer/container/error_handler/h2/
  health/macros/migration_history/multi_app/multi_tenant/orm/pay/qr_code/runtime/schema_cache/
  seed/server），LOC 降至 ~9.2K（57K → 9.2K，−83.9%）

## 后果

- 正向：sz-rust-core 从 57K LOC 降至 ~9.2K；8 个 facade（P2 七个 + P3 四个 = 11 个，含集成测试 crate）边界清晰；编译隔离（改 view 不重编 orm）；依赖方向无环（orm-ext→orm、router 独立、middleware→http/cache/orm、mvc→http/infra/middleware/orm）
- 负向：middleware 簇提取涉及安全关键代码（虽零逻辑改动，仍需人类复核）；facade 数量增多，发布矩阵复杂化（ADR-018 已定义策略）

## 注意事项

- `ScopeId` 的类型定义现位于 sz-rust-middleware-facade，core 的 container 仅是重导出；
  若未来移动 ScopeId，必须同步修改两处
- middleware 簇的 log.rs 为两个原文件合并（LogFacade + 中间件），维护时注意两部分的边界
- 后续提取（如 error_handler/health/api_version 等"易提取"模块）可复用本 ADR 的四簇模式：
  先查簇内互引用 + 簇外依赖，确认无环后整簇搬移

## Bug 定位提示

- `E0460: found possibly newer version of crate`：workspace.dependencies 中 facade 的
  `version.workspace = true` 被局部覆盖，或新 facade 的 Cargo.toml 硬编码了版本号
- 找不到 `ScopeId`：检查 sz-rust-middleware-facade 顶层定义与 core container 的 re-export 是否同步
- doctest 报 `sz_rust_core::` 找不到：搬移后的 facade 内 doc 注释仍引用 core 路径，需改为
  本 crate 路径（搬移时必须 sed 处理 doc 注释中的 crate 名）
- 全量测试出现 `crate X required to be available in rlib format`：Cargo 并发编译竞争（已知限制），
  用 `--jobs 1` 规避
