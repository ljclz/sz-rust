## 一、性能瓶颈分析与解决方案

### 1.1 瓶颈 A：执行器 Vec\<Row\> 全量物化

**现状**（`crates/szrsql-sql/src/executor.rs:24`）：
```
当前实现用 Vec<Row> 物化中间结果，简化测试与调试
```

每个算子（Scan → Filter → Projection → Join → Aggregate）都将全部行收集到 `Vec<Row>` 再传递给下一层。对于 100 万行 × 10 列的查询，中间结果占用约 80MB+ 堆内存。

**影响范围**：
- 大表全表扫描（SELECT * FROM big_table）
- 多表 JOIN（笛卡尔积中间结果）
- 子查询 / CTE 物化
- ORDER BY 全量排序

**解决方案（分阶段）**：

| 阶段 | 方案 | 工作量 | 收益 |
|------|------|--------|------|
| 短期（P10） | **流式 Limit 下推**：Limit 算子不物化全部行，Scan 产出 N 行即停止 | 小（2-3天） | 消除 LIMIT 查询的内存峰值 |
| 短期（P10） | **Filter 下推到 Scan**：WHERE 条件在 Scan 层过滤，减少中间行数 | 小（3-5天） | 减少 50-90% 中间内存 |
| 中期（P11） | **迭代器树（Volcano Iterator）**：每个算子实现 `Iterator<Item=Row>`，逐行拉取 | 大（2-3周） | 内存从 O(N) 降为 O(1)（无 Sort/HashJoin 时） |
| 中期（P11） | **向量化批处理**：`Iterator<Item=RecordBatch>`（Arrow 格式），每批 4096 行 | 大（3-4周） | CPU cache 友好 + SIMD 加速 |
| 长期（P12） | **外部排序 / Hash Spill**：Sort/HashJoin 超内存阈值时 spill 到磁盘 | 大（4-6周） | 支持超内存数据集 |

**推荐路径**：P10 先做 Limit 下推 + Filter 下推（投入小、收益明确），P11 引入迭代器树替换 Vec\<Row\> 物化。

### 1.2 瓶颈 B：WAL 单文件 Mutex

**现状**（`crates/szrsql-tx/src/wal.rs:511`）：
```rust
pub struct WalWriter {
    file: std::sync::Mutex<std::fs::File>,  // 所有写入串行化
    current_lsn: AtomicU64,
    path: PathBuf,
}
```

所有并发事务的 `append()` 必须竞争同一把 Mutex，高并发下成为吞吐瓶颈。

**已有缓解**：
- `append_batch()`：批量写入减少锁获取次数
- `WalGroupCommit`：每 128 条触发一次 fsync，摊销 IO 开销

**解决方案（分阶段）**：

| 阶段 | 方案 | 工作量 | 收益 |
|------|------|--------|------|
| 短期（P10） | **写缓冲 + 单次锁批量刷出**：每线程先写 thread-local buffer，由后台线程定时（1ms）或达阈值时一次性持锁写入 | 中（1周） | 锁持有时间从 N×write 降为 1×write_all |
| 中期（P11） | **WAL 分段文件**：按 LSN 范围分多个文件（如每 64MB 一段），写入时仅锁当前段 | 中（1-2周） | 减少锁粒度 + 支持并行归档 |
| 中期（P11） | **io_uring / 异步写入**：WAL 写入改为 tokio::fs 或 io_uring，Mutex 换为 tokio::Mutex | 中（1周） | 写入不阻塞 CPU 线程 |
| 长期（P12） | **多 WAL 通道（Group Commit 增强）**：N 个 writer 线程各自持有独立文件段，LSN 通过 AtomicU64 全局分配，fsync 由 coordinator 统一触发 | 大（3-4周） | 写入吞吐线性扩展 |

**推荐路径**：P10 先做写缓冲（改动最小，效果显著），P11 引入分段文件 + 异步写入。

### 1.3 性能基准参考

当前 Group Commit 配置（batch_threshold=128）下，WAL 写入吞吐约 **50K-80K records/s**（单线程 append + 批量 fsync）。瓶颈主要在 fsync 延迟（SSD ~0.1ms，HDD ~5ms）。

### 2.4 SzRSQL 优势

1. **Rust 内存安全**：无 use-after-free / buffer overflow / data race（编译期保证）
2. **多协议兼容**：单进程同时支持 PG/MySQL/TDS/Oracle 四种协议（独特）
3. **AI 原生集成**：MCP server 35 工具 + NL2SQL + RAG（业界首创）
4. **CDC 内置**：无需外部 Debezium，引擎层直接分发变更事件
5. **分布式就绪**：Raft + Percolator + Multi-Master 代码已实现（待启用）
6. **轻量部署**：单二进制文件，无外部依赖（对比 PG 需 initdb + 配置）
7. **安全能力完整**：RBAC/RLS + 审计/防火墙/TDE/脱敏（szrsql-security crate）

### 2.5 SzRSQL 劣势

1. **存储引擎不成熟**：Vec\<Row\> 主存储，无真实分页/缓冲池管理（Volcano 迭代器已实现但未集成）
2. **RPO > 0**：5 秒快照间隔，崩溃可能丢失最近事务
3. **无并行查询**：单线程执行，无并行扫描/Join/聚合
4. **无自动故障转移**：Raft 代码就绪但未启用，无 HA 机制
5. **生态空白**：无驱动库（JDBC/ODBC/ORM）、无监控集成（Prometheus/Grafana 仅骨架）
6. **未经生产验证**：无真实业务负载跑过

## 六、总结

SzRSQL 是一个**架构设计完整、核心模块真实、但生产验证不足**的早期数据库项目。

- **架构层面**（85 分）：多协议、多引擎、分布式、CDC、AI 集成的设计蓝图完整
- **实现层面**（65 分）：核心路径（协议/事务/执行/CDC）真实可工作，但存储引擎和优化器是短板
- **生产层面**（40 分）：无真实业务验证、无 HA、RPO>0、无生态工具

**一句话定位**：SzRSQL 当前是一个"功能原型"（Functional Prototype），而非"生产就绪产品"。距离生产可用还需 6-12 个月的核心引擎加固工作。
