## 1. 概述

### 1.1 文档目的

本清单针对 SzRSQL 数据库进行系统化的对抗性边界审计，覆盖 SQL 解析、内存管理、并发控制、网络协议、数据一致性及极端值边界等六大类别，共计 **60 项** 审计用例。每项用例均针对数据库在恶意或极端输入下可能暴露的安全漏洞与稳定性缺陷。

### 1.2 适用场景

- 安全发布前的边界审计
- 回归测试补充依据
- Fuzzing 测试用例生成输入
- 代码审计与渗透测试参考
- 升级与重构后的破坏性验证

### 1.3 项目背景关键约束

| 维度 | 现状 |
| --- | --- |
| 存储引擎 | WAL 持久化 + B+Tree 持久化存储 + BufferPool 刷盘 + 崩溃恢复 + 远程存储（S3/HTTP）+ Spill 溢写盘 |
| 共识协议 | Raft |
| 事务模型 | Percolator（基于时间戳的分布式事务） |
| 协议 | pgwire（PostgreSQL 线协议） |
| 语言 | Rust（内存安全由编译器保证，但逻辑错误仍可能发生） |
| 事务模型风险 | commit-then-log（ACK 丢失风险，待改为 log-then-commit） |

> **重要说明**：尽管 Rust 从语言层面消除了内存不安全（如 buffer overflow、use-after-free），但**逻辑性资源耗尽、并发竞态、协议畸形输入、数据一致性破坏**等仍可能发生，本清单聚焦于这些领域。
>
> **v1.2 纠正说明**：v1.1 中错误描述项目为"纯内存数据库，无持久化"，实际项目具备完整的持久化实现（详见 `szrsql-tx/src/wal.rs`、`szrsql-storage/src/buffer.rs`、`szrsql-replication/src/backup.rs`）。本清单所有基于"内存数据库"前提的测试项需重新评估其在持久化场景下的行为。

## 2. 审计范围与原则

### 2.1 审计范围

| 类别 | 编号区间 | 项数 |
| --- | --- | --- |
| SQL 注入与解析边界 | ADV-SQL-001 ~ ADV-SQL-010 | 10 |

| 并发与竞态条件 | ADV-CON-001 ~ ADV-CON-010 | 10 |
| 协议与网络安全 | ADV-NET-001 ~ ADV-NET-010 | 10 |
| 数据完整性与一致性 | ADV-DAT-001 ~ ADV-DAT-010 | 10 |
| 边界条件与极端值 | ADV-EDG-001 ~ ADV-EDG-010 | 10 |

### 2.2 风险等级定义

| 等级 | 定义 | 响应要求 |
| --- | --- | --- |
| **Critical** | 可导致数据丢失、RCE、认证绕过、系统崩溃 | 发布前必须修复 |
| **High** | 可导致服务拒绝、数据不一致、关键功能失效 | 发布前必须修复或提供缓解措施 |
| **Medium** | 可导致性能退化、边缘场景错误、潜在漏洞 | 限期修复 |
| **Low** | 仅在极端构造下触发，影响有限 | 评估后决定 |

### 2.3 状态定义

| 状态 | 含义 |
| --- | --- |
| **待测试** | 尚未执行测试 |
| **通过** | 测试通过，符合预期行为 |
| **失败** | 测试失败，发现缺陷 |
| **已修复** | 缺陷已修复并通过回归 |

### 2.4 审计原则

1. **真实执行**：每项必须在真实环境中执行，禁止仅基于代码推断结论。
2. **独立验证**：审计结论必须由独立测试用例验证，而非依赖开发者声明。
3. **边界优先**：聚焦正常路径之外的边界、极端、恶意构造输入。
4. **可复现**：每项必须提供可复现的测试步骤与输入数据。
5. **无假设**：不假设 Rust 内存安全等于逻辑安全，不假设现有测试已覆盖。

### 3.3 并发与竞态条件

> **类别编号**：ADV-CON
> **审计目标**：验证 Percolator 事务模型与 Raft 共识在并发场景下的正确性。

| 测试 ID | 测试名称 | 测试描述 | 预期行为 | 测试方法 | 风险等级 | 状态 |
| --- | --- | --- | --- | --- | --- | --- |
| ADV-CON-001 | 死锁检测 | 两个事务交叉锁等待，测试死锁检测与自动解除 | 应在合理时间内检测死锁并回滚其中一个事务 | 1. T1: `BEGIN; UPDATE t SET v=1 WHERE id=1;`<br>2. T2: `BEGIN; UPDATE t SET v=1 WHERE id=2;`<br>3. T1: `UPDATE t SET v=1 WHERE id=2;`（阻塞）<br>4. T2: `UPDATE t SET v=1 WHERE id=1;`（应触发死锁）<br>5. 验证一个事务被回滚，另一个完成 | Critical | ✅ 通过 |

### 6.3 已发现并修复的缺陷

#### 缺陷 #001：解析器对深度嵌套 OR/AND 链栈溢出（已修复）

| 字段 | 内容 |
| --- | --- |
| 缺陷编号 | ADV-BUG-001 |
| 关联审计项 | ADV-SQL-004 / ADV-MEM-003 |
| 风险等级 | **High** |
| 发现日期 | 2026-07-24 |
| 修复日期 | 2026-07-24 |
| 复现命令（修复前） | `cargo test -p szrsql-sql --test adversarial test_adv_sql_004_long_sql_input` |
| 复现输入（修复前） | `SELECT * FROM users WHERE id = 0 OR id = 1 OR ... OR id = 49`（50 个 OR 链） |
| 修复前行为 | 进程栈溢出崩溃（`STATUS_STACK_OVERFLOW`, exit code `0xc00000fd`） |
| 修复后行为 | 三层防护生效：1. SQL 长度预检 `MAX_SQL_LEN=1MB` 拒绝超长输入；2. OR/AND 链深度预检 `MAX_BINARY_OP_CHAIN=32` 限制二值表达式链长度；3. 表达式递归深度限制 `MAX_EXPR_DEPTH=512` 防止栈溢出 |
| 根因分析 | `szrsql-sql` 解析器使用递归下降解析，二值表达式（AND/OR）的左结合性导致递归深度与表达式项数成正比，无深度限制保护 |
| 修复方案 | 1. 在 parser 中添加 `MAX_SQL_LEN`、`MAX_BINARY_OP_CHAIN`、`MAX_EXPR_DEPTH` 三层深度计数器<br>2. 超限时返回 `ParseError` 而非继续递归<br>3. 在 `lib.rs` 中导出常量供外部配置 |
| 状态 | ✅ **已修复并通过回归** |

#### 缺陷 #002：多语句解析未限制（已修复）

| 字段 | 内容 |
| --- | --- |
| 缺陷编号 | ADV-BUG-002 |
| 关联审计项 | ADV-SQL-009 |
| 风险等级 | **High** |
| 发现日期 | 2026-07-24 |

| 根因分析 | 解析器接受分号分隔的多语句，但未提供"单语句模式"开关 |
| 修复方案 | 1. 在 `parse_sql` 之外提供 `parse_single_statement` 函数<br>2. pgwire 服务端默认 `allow_multi_statement=false`<br>3. 文档明确多语句行为 |
