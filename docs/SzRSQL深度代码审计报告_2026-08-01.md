## 一、运行时实际架构（基于 main.rs 代码证据）

### 1.1 数据存储：Vec<Row> + 可选 B+Tree 索引 + 可选 BufferPool 分页

`InMemoryTable`（<ksymbol name="InMemoryTable" filename="executor.rs" path="crates/szrsql-sql/src/executor.rs" startline="956" type="class">InMemoryTable</ksymbol>）是实际运行时的核心数据结构，包含：

- **`rows: Vec<Row>`** — 主数据存储，所有 DML 操作直接读写此数组
- **`deleted: HashSet<usize>`** — tombstone 标记，逻辑删除
- **`xmin/xmax: Vec<u32>`** — MVCC 版本元数据（与 rows 等长）
- **`pk_index: Option<BTree>`** — 可选 B+Tree 主键索引（<ksymbol name="enable_btree_pk" filename="executor.rs" path="crates/szrsql-sql/src/executor.rs" startline="1114" type="function">enable_btree_pk</ksymbol>），仅支持 Int64 类型
- **`persistence: Option<Arc<BufferPool>>`** — 可选 BufferPool 持久化后端
- **`paged_storage: Option<Arc<BufferPool>>`** — 可选分页存储（10 万行阈值后自动 spill）

**代码证据**（main.rs L721-763）：
```rust
// OPT-3：为每张已加载的表启用 BufferPool 持久化后端
for (name, table_arc) in &loaded_tables {
    let db_path = data_dir.join(format!("{name}.db"));
    table.enable_persistence(&db_path)?;
    // P1-1：启用分页存储主路径
    table.enable_paged_storage(&paged_path)?;
}
```

**结论**：B+Tree 和 BufferPool **已经接入运行时**，不是死代码。但它们是 `InMemoryTable` 的可选后端，不是存储引擎的替代。数据始终以 `Vec<Row>` 为主存，B+Tree 提供主键点查加速，BufferPool 提供分页持久化镜像。

```rust
fn mvcc_insert(&self, table, row, table_name) -> usize {
    if let Some(mvcc) = self.mvcc {
        if self.mvcc_txn_id != 0 {
            let row_id = table.insert_row_versioned(row.clone(), self.mvcc_txn_id);
            let key = format!("{}:{}", table_name.name.to_lowercase(), row_id);
            let _ = mvcc.register_write(self.mvcc_txn_id, &key);
            return row_id;
        }
    }
    // 未启用时退化为普通 insert
}
```

**结论**：MVCC **已完全接入运行时**。每个 session 的 BEGIN/COMMIT/ROLLBACK 同步到 MvccManager 状态机，SELECT/UPDATE/DELETE 使用 `scan_with_versions` + `is_visible` 过滤，INSERT 使用 `insert_row_versioned` 设置 xmin。支持 ReadCommitted/RepeatableRead/Serializable 三种隔离级别，包含 SSI 写偏斜检测。

- Insert/Update/Delete — 行级变更

```rust
fn dist_dual_write(&self, table_name, row_id, row) {
    let handle = match &self.dist_runtime { Some(h) => h, None => return };
    // Autocommit：即时 2PC（begin → prewrite → commit）
    let mut txn = DistTxnClient::new(&mut *rt);

}
```

### 1.5 持久化：JSON 快照 + WAL + BufferPool 分页 三层互补

| 层次 | 机制 | 文件格式 | 触发时机 |
|------|------|---------|---------|
| **快照** | `tables.json` 全量序列化 | JSON | 启动加载 + 每5秒增量保存 + 关闭保存 |
| **WAL** | `wal.log` 行级变更记录 | 二进制 | 每次 COMMIT fsync |
| **分页** | `{table}.paged` 按行分页 | 二进制（BufferPool） | 10万行阈值自动 spill |

**崩溃恢复流程**（main.rs L600-713）：
1. 加载 JSON 快照（基础数据）
2. 回放 WAL TableData 记录（增量提交）
3. 为每张表启用 BufferPool 持久化后端
4. 为每张表启用分页存储后端

## 四、同类数据库深度对比分析

### 4.1 与 PostgreSQL 对比

| 维度 | SzRSQL | PostgreSQL | 评价 |
|------|--------|-----------|------|
| **协议** | pgwire v3.0 兼容 | 原生 pgwire | SzRSQL 客户端驱动可直接连接 |

## 七、核心结论

### SzRSQL 是什么？

SzRSQL 是一个**以 Rust 实现的、多协议兼容的 SQL 数据库**，当前实际运行在 `Vec<Row>` 内存表 + MVCC + WAL + 可选 B+Tree 索引 + 可选 BufferPool 分页持久化的架构上。与早期审计报告所说的"未接入运行时"不同，MVCC、WAL、行级锁、B+Tree 索引、BufferPool 持久化、分布式运行时（单节点）、CDC、流复制等组件**均已在运行时路径中**。

### SzRSQL 不是什么？

SzRSQL **不是**一个 B+Tree 磁盘存储引擎的数据库。数据的主路径是 `Vec<Row>` 内存数组，B+Tree 仅作为可选的主键索引加速，BufferPool 仅作为可选的持久化镜像。这与 PostgreSQL 的"堆表 + B+Tree 索引"架构有本质区别。

### 最大竞争优势

**5 种数据库协议同时兼容**（pgwire + MySQL + TDS + Oracle + SQLite JSON）是 SzRSQL 在所有对比数据库中独一无二的优势。没有其他开源数据库能做到同一进程同时支持 5 种不同数据库协议。

### 最大技术风险

**内存为主的存储架构**是最大的技术风险。Vec<Row> 全内存意味着数据规模受限于内存大小，10M+ 行时性能和内存压力会成为瓶颈。需要尽快将 B+Tree 升级为主存储引擎。
