# SzRSQL 生产试点方案

- **文档版本**：v1.0
- **日期**：2026-07-26
- **试点对象**：SzRSQL v1.0.0-rc.1（`Cargo.toml:25` workspace.package.version）
- **文档状态**：草案（待试点团队评审后定稿）

> **重要声明**：
> 1. 本方案中的成功标准（如 P99 < 50ms、可用性 ≥ 99.9%）为**承诺目标**，不是已达成值。
> 2. 本方案不引用任何虚构的生产案例。候选场景均为**候选**，需经业务方确认后纳入试点。
> 3. 试点过程中产生的所有数据（性能、可用性、一致性）需以实际监控为准，不以本文档的目标值替代。
> 4. 试点前必须完成第三方安全审计（见 `docs/第三方安全审计委托书.md`）与自审计残留 Critical/High 项修复（见 `docs/安全自审计清单.md` §4.1/§4.2）。

---

## 1. 试点目标

在 1-2 个内部业务中验证 SzRSQL 的生产可用性，具体目标如下：

1. **功能兼容性**：验证 SzRSQL 与现有 PostgreSQL 业务 SQL 的兼容性（pgwire 协议层兼容）。
2. **性能可接受性**：在真实业务负载下，验证 P99 延迟、吞吐量是否满足业务要求。
3. **可用性**：验证单机/主从部署下的可用性是否达到承诺目标。
4. **数据一致性**：通过双写对比验证 SzRSQL 与现有 PostgreSQL 的数据一致性。
5. **运维可控性**：验证备份、监控、告警、故障恢复流程是否完备。
6. **风险识别**：识别生产环境中可能暴露的边界问题（如长事务、大查询、连接耗尽）。

> 试点**不**以取代现有数据库为目标，而是以"验证可用性 + 暴露问题"为目标。

## 2. 试点场景选择标准

候选场景必须**同时**满足以下条件：

| 维度 | 标准 | 说明 |
|------|------|------|
| 业务重要性 | 非核心业务 | 故障可容忍，不影响主营收 |
| 数据量 | < 100GB | 单机可承载，避免分布式复杂度 |
| QPS | < 1000 | 单机可承载 |
| 读写比 | > 3:1（读多写少） | SzRSQL 的 MVCC + B+Tree 适合读多写少 |
| 事务复杂度 | 无复杂分布式事务 | 避免触发 Percolator 路径（试点阶段不验证分布式事务） |
| SQL 复杂度 | 中等以下 | 避免 OLAP 复杂 JOIN，避免存储过程/触发器（试点阶段不验证 PL/pgSQL 完整性） |
| 数据敏感度 | 内部数据 | 避免直接试点用户隐私数据 |
| 回滚成本 | 低 | 业务方具备快速回滚到 PostgreSQL 的能力 |

> 不满足任一条件的场景，**禁止**纳入试点。

## 3. 候选试点场景

以下 3 个场景为**候选**，需经业务方确认数据量/QPS/读写比后纳入试点。试点期间实际指标以监控为准。

### 3.1 场景 A：内部配置中心

- **业务描述**：存储应用配置（KV）+ 配置历史版本查询。
- **数据特征**：
  - 数据量预估：1-10GB
  - QPS 预估：100-500
  - 读写比预估：10:1（配置读取远多于变更）
  - 事务复杂度：单行更新为主
- **适配性**：
  - ✅ 数据量、QPS、读写比均满足标准
  - ✅ SQL 简单（KV 读写 + 历史版本范围查询）
  - ⚠️ 配置变更需保证强一致，需验证 SzRSQL 的 MVCC + WAL 同步策略
- **候选试点优先级**：高

### 3.2 场景 B：审计日志存储

- **业务描述**：时序写入审计日志 + 偶发查询（合规审计、问题排查）。
- **数据特征**：
  - 数据量预估：10-80GB
  - QPS 预估：500-1000（写入为主）
  - 读写比预估：1:10（写多读少）
  - 事务复杂度：单行插入为主
- **适配性**：
  - ⚠️ 读写比 < 3:1（不满足标准），但写入 QPS 适中，可考虑纳入
  - ✅ SQL 简单（INSERT + 时间范围 SELECT）
  - ✅ 可利用 SzRSQL 审计日志模块（`crates/szrsql-security/src/audit.rs` 哈希链）形成"审计日志存审计日志"的闭环
- **候选试点优先级**：中

### 3.3 场景 C：用户行为分析（OLAP 只读副本）

- **业务描述**：在只读副本上执行 OLAP 查询，分析用户行为。
- **数据特征**：
  - 数据量预估：50-100GB
  - QPS 预估：10-100（复杂查询为主）
  - 读写比预估：100:1（纯只读）
  - 事务复杂度：长查询为主
- **适配性**：
  - ✅ 读写比满足标准
  - ⚠️ SQL 复杂度可能超标准（多表 JOIN、聚合），需逐查询评估
  - ⚠️ 长查询可能触发 SzRSQL 的 MVCC 版本堆积，需验证 Vacuum 效果（`crates/szrsql-tx/src/vacuum.rs` / `autovacuum.rs`）
- **候选试点优先级**：低（建议在场景 A/B 稳定后再纳入）

## 4. 试点阶段划分

试点总周期**目标** 12 周，分 4 个阶段。每个阶段设置明确的进入条件、退出条件与回滚条件。

### 4.1 阶段 1：单机部署 + 数据迁移 + 功能验证（1-2 周）

**进入条件**：
- 第三方安全审计完成，Critical/High 漏洞已修复并通过复核
- 试点场景已与业务方确认
- 试点团队已就位（DBA + SRE + 开发）

**任务**：
1. 部署 SzRSQL v1.0.0-rc.1 单机实例（基于 `szrsql-bin`）。
2. 配置 TLS 1.3 强制（参考 `crates/szrsql-protocol/src/pgwire/tls.rs`，禁用明文回退）。
3. 配置 TDE 透明加密（参考 `crates/szrsql-security/src/tde.rs`，主密钥从 passphrase 派生）。
4. 配置 SCRAM-SHA-256 认证（禁用 trust 模式）。
5. 配置备份策略（基于 `crates/szrsql-replication/` 备份模块）。
6. 从现有 PostgreSQL 导出试点业务数据（pg_dump），导入 SzRSQL。
7. 执行功能验证：
   - 业务 SQL 全量回归（与应用方共同验证）
   - 边界场景测试（空表、单行、大表、长事务）
8. 配置监控（Prometheus + Grafana + AlertManager，参考 `crates/szrsql-ops/` Grafana 模块）。

**退出条件**：
- 功能验证 100% 通过
- 业务 SQL 全部可执行
- 监控告警就位

**回滚条件**：
- 功能验证失败率 > 5%
- 数据迁移出现不可恢复错误
- → 回滚到 PostgreSQL，保留 SzRSQL 实例供问题分析

### 4.2 阶段 2：双写对比（2-4 周）

**进入条件**：
- 阶段 1 退出条件全部满足

**任务**：
1. 应用层改造为双写模式：同时写入 PostgreSQL 与 SzRSQL。
2. 双写采用"PostgreSQL 为主，SzRSQL 为辅"策略，写入失败以 PostgreSQL 为准。
3. 部署对比工具（参考 `crates/szrsql-shadow/` 影子流量对比模块）：
   - 实时对比两侧读取结果
   - 记录差异行与差异原因
4. 每日生成对比报告，差异率需 < 0.01%。
5. 监控双写延迟（SzRSQL 写入延迟应 < 100ms）。

**退出条件**：
- 连续 7 天差异率 = 0
- 双写延迟稳定 < 100ms
- 无未解释的差异

**回滚条件**：
- 差异率 > 0.1%
- 双写延迟 > 1s
- → 停止 SzRSQL 双写，应用层回退到仅写 PostgreSQL

### 4.3 阶段 3：流量切换（4-8 周）

**进入条件**：
- 阶段 2 退出条件全部满足

**任务**：
1. **第 4-5 周**：切换 10% 读流量到 SzRSQL（写流量仍双写）。
2. **第 5-6 周**：评估 10% 流量下的性能与可用性，若达标则切换至 50%。
3. **第 6-7 周**：评估 50% 流量下的性能与可用性，若达标则切换至 100%。
4. **第 7-8 周**：100% 读流量切换后，停止双写，SzRSQL 成为唯一写入端（PostgreSQL 降级为只读备份）。
5. 每个流量阶段记录：
   - P50/P95/P99 延迟
   - QPS
   - 错误率
   - 资源使用率（CPU/内存/磁盘/网络）

**退出条件**：
- 100% 流量下连续 7 天满足成功标准（见 §6）
- 无 P0/P1 故障

**回滚条件**：
- 任意流量阶段 P99 > 100ms 或错误率 > 0.1%
- 发生 P0 故障
- → 立即回滚到 PostgreSQL（回滚时间目标 < 5 分钟，见 §5.2）

### 4.4 阶段 4：稳定运行 + 监控告警验证 + 故障演练（8-12 周）

**进入条件**：
- 阶段 3 退出条件全部满足

**任务**：
1. SzRSQL 作为唯一数据库运行，连续观察 4 周。
2. **监控告警验证**：
   - 模拟磁盘满、内存压力、连接耗尽、长事务等场景
   - 验证告警是否及时触发（告警延迟 < 1 分钟）
   - 验证告警准确性（无误报、漏报）
3. **故障演练**：
   - 模拟 SzRSQL 进程崩溃 → 验证崩溃恢复（参考 `crates/szrsql-tx/src/crash_recovery_fuzz.rs`）
   - 模拟磁盘故障 → 验证备份恢复
   - 模拟网络分区（若部署主从）→ 验证 Raft 选举（参考 `crates/szrsql-dist/src/raft.rs`）
4. **性能基线**：建立稳定运行期的性能基线，作为后续版本回归对比。

**退出条件**：
- 连续 4 周满足成功标准（见 §6）
- 故障演练全部通过（RTO < 30 分钟，RPO = 0）
- 监控告警无遗漏

**回滚条件**：
- 发生 P0 故障且 RTO > 30 分钟
- 发生数据丢失（RPO > 0）
- → 回滚到 PostgreSQL，启动数据迁移（从 SzRSQL 导出未丢失数据）

## 5. 风险评估与回滚方案

### 5.1 风险评估

| 风险类别 | 风险描述 | 概率 | 影响 | 缓解措施 |
|---------|---------|------|------|---------|
| 数据丢失 | SzRSQL 崩溃导致数据丢失 | 中 | 高 | WAL 同步 + 每日备份 + 双写对比（阶段 2） |
| 服务中断 | SzRSQL 不可用导致业务中断 | 中 | 高 | 双活部署（PostgreSQL 降级为只读备份，可快速切回） |
| 性能退化 | SzRSQL 在真实负载下性能不达标 | 中 | 中 | 压测 + 限流 + 降级（读流量切回 PostgreSQL） |
| 数据不一致 | SzRSQL 与 PostgreSQL 数据不一致 | 低 | 高 | 双写对比（阶段 2）+ 差异率监控 |
| 安全漏洞 | SzRSQL 存在未发现的安全漏洞 | 低 | 高 | 第三方安全审计 + 自审计（试点前完成） |
| 运维失误 | 误操作导致数据损坏 | 中 | 中 | DBA 培训 + 操作审计（`crates/szrsql-security/src/audit.rs`） |
| 兼容性问题 | 业务 SQL 在 SzRSQL 上行为异常 | 中 | 中 | 阶段 1 功能验证 + 阶段 2 双写对比 |

### 5.2 回滚方案

#### 5.2.1 快速回滚（< 5 分钟）

适用于阶段 3 流量切换期：

1. 应用层切换读流量到 PostgreSQL（PostgreSQL 在阶段 3 仍作为只读备份）。
2. 停止 SzRSQL 写入，应用层回退到仅写 PostgreSQL。
3. 验证 PostgreSQL 数据完整性。
4. 通知业务方回滚完成。

> 快速回滚依赖 PostgreSQL 在阶段 3 始终保持只读备份状态，且双写在阶段 3 仍持续。

#### 5.2.2 数据迁移回滚（< 30 分钟）

适用于阶段 4（PostgreSQL 已停止双写）：

1. 从 SzRSQL 导出最新数据（pg_dump 兼容格式）。
2. 导入 PostgreSQL。
3. 应用层切换到 PostgreSQL。
4. 验证数据完整性。

> 数据迁移回滚依赖 SzRSQL 的 pg_dump 兼容导出能力，需在阶段 1 验证。

#### 5.2.3 灾难回滚（数据丢失场景）

1. 从最近备份恢复 PostgreSQL。
2. 应用层切换到 PostgreSQL。
3. 评估数据丢失范围，通知业务方。
4. 启动问题分析（保留 SzRSQL 实例与日志）。

> 灾难回滚的 RPO 取决于备份频率，目标 RPO = 0 需 WAL 同步复制（见 `crates/szrsql-replication/`）。

## 6. 成功标准

以下标准为**承诺目标**，试点期间实际值以监控为准。若连续 7 天未达标，触发回滚评估。

### 6.1 功能标准

- **业务 SQL 兼容性**：100% 兼容现有业务 SQL（阶段 1 验证）。
- **数据一致性**：与 PostgreSQL 对照零差异（阶段 2 验证，差异率 = 0）。

### 6.2 性能标准（承诺目标）

| 指标 | 目标 | 测量方法 |
|------|------|---------|
| P50 延迟 | < 10ms | Prometheus 直方图 |
| P95 延迟 | < 30ms | Prometheus 直方图 |
| P99 延迟 | < 50ms | Prometheus 直方图 |
| QPS | ≥ 业务峰值 QPS | Prometheus 计数器 |
| 错误率 | < 0.01% | 应用层错误日志 |

### 6.3 可用性标准（承诺目标）

- **可用性**：≥ 99.9%（月度，扣除计划维护时间）
- **计算公式**：`可用时间 / (总时间 - 计划维护时间)`
- **目标 RTO**：< 30 分钟（灾难恢复）
- **目标 RPO**：0（WAL 同步复制，需主从部署）

### 6.4 运维标准

- 监控告警覆盖率：100%（所有关键指标）
- 告警延迟：< 1 分钟
- 故障演练通过率：100%
- 备份恢复演练：每月 1 次，成功率 100%

## 7. 监控告警

### 7.1 监控栈

- **指标采集**：Prometheus（参考 `crates/szrsql-ops/` Grafana 模块）
- **可视化**：Grafana（参考 `crates/szrsql-ops/` Grafana 仪表盘）
- **告警**：AlertManager
- **日志**：Loki 或 ELK（采集 SzRSQL 审计日志，参考 `crates/szrsql-security/src/audit.rs`）
- **追踪**：OpenTelemetry + Jaeger（参考 `crates/szrsql-ops/` OTel 模块）

### 7.2 关键指标

| 指标类别 | 指标 | 告警阈值（目标） |
|---------|------|-----------------|
| 性能 | P99 延迟 | > 50ms 持续 1 分钟 → P2 告警 |
| 性能 | QPS 异常下降 | 较基线下降 > 50% 持续 5 分钟 → P1 告警 |
| 错误 | 错误率 | > 0.1% 持续 1 分钟 → P1 告警 |
| 资源 | CPU 使用率 | > 80% 持续 5 分钟 → P2 告警 |
| 资源 | 内存使用率 | > 85% 持续 5 分钟 → P2 告警 |
| 资源 | 磁盘使用率 | > 80% → P2 告警；> 90% → P1 告警 |
| 资源 | 磁盘 IO 等待 | > 20ms 持续 5 分钟 → P2 告警 |
| 可用性 | 进程存活 | 进程退出 → P0 告警 |
| 可用性 | 端口可达 | 端口不可达持续 30 秒 → P0 告警 |
| 一致性 | 双写差异率 | > 0.01% → P1 告警 |
| 一致性 | 双写延迟 | > 100ms 持续 1 分钟 → P2 告警 |
| 事务 | 长事务 | > 60 秒 → P2 告警 |
| 事务 | 死锁 | 任意死锁 → P1 告警 |
| 复制 | 主从复制延迟 | > 1 秒持续 1 分钟 → P2 告警 |
| 安全 | 认证失败率 | > 10 次/分钟 → P1 告警（疑似暴力破解） |

### 7.3 告警分级

| 级别 | 含义 | 响应时间（目标） |
|------|------|-----------------|
| P0 | 服务不可用 | 5 分钟内响应 |
| P1 | 严重降级 | 15 分钟内响应 |
| P2 | 轻微降级 | 1 小时内响应 |
| P3 | 容量预警 | 工作日响应 |
