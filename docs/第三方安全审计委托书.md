## 1. 审计目标

对 SzRSQL v1.0.0-rc.1 进行独立的第三方安全审计，目标如下：

1. **发现并量化安全风险**：覆盖 OWASP Top 10（2021）、CWE Top 25（2024）以及数据库内核特有的安全风险类别。
2. **数据库特有安全风险**至少覆盖以下子项：
   - SQL 注入（含二阶注入、方言混淆注入、DDL 标识符注入）
   - 认证绕过（SCRAM-SHA-256、密码策略、会话劫持）
   - 权限提升（RBAC / RLS / 多租户隔离绕过）
   - 数据泄露（TDE 静态数据、列级加密、备份加密、远程存储鉴权）
   - 协议安全（pgwire v3.0、TLS 1.3、降级攻击、COPY/LISTEN-NOTIFY 滥用）
3. **出具独立审计报告**，并对发现的漏洞给出可复现 PoC 与修复建议。
4. **协助 CVE 编号申请**：对评定为 High/Critical 的漏洞，由受托方协助走 CVE 流程。
5. **复核修复结果**：开发团队修复完成后，由受托方复核并出具复核报告。

> 审计范围不包括：性能基准测试、功能正确性验证（这些由 `docs/大数据量对比测试报告.md`、`docs/全面排查汇总报告.md` 等既有流程覆盖）。

## 3. 审计标准

### 3.1 主标准

- **OWASP ASVS Level 2**：作为应用安全验证的主清单。
- **CWE Top 25 (2024)**：作为危险软件弱点的对照清单。
- **ISO/IEC 27001:2022**：附录 A 控制项作为信息安全管理体系对照。

### 3.2 数据库特有标准

参考 PostgreSQL、MySQL 官方安全审计清单，补充以下数据库内核审计项：

- **认证**：SCRAM-SHA-256 实现正确性（参考 RFC 7677）、密码策略、会话固定/劫持。
- **授权**：RBAC 权限检查的覆盖完整性、RLS 谓词注入风险、越权访问。
- **SQL 注入**：DDL 路径二阶注入（参考 ADR 0007 标识符转义）、多语句防护、方言混淆。
- **加密**：TDE AES-256-CTR 实现正确性、列加密 AES-256-GCM、密钥管理与轮换。
- **协议**：pgwire v3.0 报文解析鲁棒性、TLS 1.3 证书校验、降级攻击防护。
- **持久化**：WAL 完整性、崩溃恢复、备份加密、远程存储鉴权（S3/HTTPFS）。
- **分布式**：Raft 选举安全性、Percolator 事务原子性、HLC 时钟偏差。

### 3.3 风险评级

采用 CVSS v3.1 评分，结合以下等级映射：

| 等级 | CVSS 评分 | 处置时限（目标） |
|------|----------|-----------------|
| Critical | 9.0 - 10.0 | 7 天内修复 |
| High | 7.0 - 8.9 | 14 天内修复 |
| Medium | 4.0 - 6.9 | 30 天内修复 |
| Low | 0.1 - 3.9 | 下一个 minor 版本修复 |

> 处置时限为目标值，实际以双方协议为准。

## 4. 审计方法

### 4.1 白盒审计（源代码审计）

- 对重点 4 个 crate 进行逐文件审计，每文件记录审计人、审计日期、发现项。
- 对非重点 crate 进行抽样审计，抽样比例 ≥ 30%（按文件数）。
- 使用 `cargo audit` / `cargo deny` 进行依赖审计。
- 对所有 `unsafe` 块、所有 `unwrap()` / `expect()` / `panic!()` 调用进行 100% 审查。
- 对所有 `format!` / 字符串拼接涉及 DDL 标识符的位置，验证是否调用 `quote_ident`（参考 ADR 0007）。

### 4.2 黑盒审计（模糊测试与渗透测试）

- **协议级模糊测试**：基于 pgwire v3.0 报文格式生成畸形报文（参考 `crates/szrsql-protocol/tests/adversarial_net.rs` 已有案例进行扩展）。
- **SQL 注入模糊测试**：基于 `crates/szrsql-security/src/sqli_detector.rs` 的 12 种注入特征构造变体用例。
- **认证渗透**：针对 SCRAM-SHA-256 流程的暴力破解、重放攻击、时间盲注。
- **权限提升渗透**：构造跨 schema、跨 tenant 的越权访问用例（参考 `crates/szrsql-catalog` 的 RBAC/RLS/Multitenant）。
- **加密强度测试**：对 TDE 加密文件、列加密密文进行密码学分析（验证 IV 唯一性、Nonce 不重复、Tag 校验严格性）。

### 4.3 灰盒审计（协议级测试）

- 在已知内部结构的前提下，针对 pgwire v3.0 协议状态机进行边界测试。
- 验证 TLS 1.3 握手在以下场景下的行为：
  - 客户端证书校验缺失
  - 协议降级尝试（TLS 1.2 → TLS 1.3 强制）
  - 证书过期 / 证书 CN 不匹配
- 验证 COPY / LISTEN-NOTIFY 在异常断连下的资源回收。

## 5. 审计交付物

### 5.1 漏洞清单

每一项漏洞记录包含：

1. 漏洞编号（受托方内部编号）
2. CWE 分类（对应 CWE Top 25 编号）
3. CVSS v3.1 评分与向量
4. 风险等级（Critical/High/Medium/Low）
5. 影响版本（v1.0.0-rc.1，若涉及更早版本需注明）
6. 受影响代码位置（精确到文件:行号）
7. 复现步骤（含 PoC 代码或脚本）
8. 修复建议（含具体代码改动方向）
9. 修复后预期行为

### 5.2 CVE 编号申请

- 对评定为 Critical / High 的漏洞，受托方协助委托方向 CVE 编号机构（CNA）申请 CVE 编号。
- 委托方在 CVE 公开前 90 天内完成修复与发布。

### 5.3 风险评级汇总表

按等级汇总漏洞数量，给出整体风险态势评估。

### 5.4 复核报告

开发团队修复完成后，受托方在 5 个工作日内完成复核，对每项修复给出：

- 复核结论（通过 / 不通过 / 部分通过）
- 复核方法（代码审查 / 测试复现 / 回归测试）
- 残留风险（如有）

### 5.5 最终审计报告

合并上述交付物，形成可对外公开的最终审计报告（脱敏后版本可公开发布）。

## 6. 审计周期

- **总周期（目标）**：4-6 周，自双方签署之日起计算。
- **阶段划分（目标）**：

| 阶段 | 周期 | 内容 |

> 实际周期可能因漏洞数量与修复难度调整，调整需双方书面确认。
