## 一、背景与动机

sz-rust 当前通过华为云码道 CodeArts 的 SDD 模式进行 AI 辅助开发，积累了 14 个真实 SDD 案例（`p3_perf_opt` / `fix_iron_violations` / `sz_orm_upgrade_3_4_0` 等）。

本文档回答一个问题：**当 sz-rust 需要自建 AI 编程 Agent 能力时，如何借鉴 Loopra 的架构设计，同时融合码道 SDD 的"规格先行"理念？**

### 1.1 两个参考坐标

| 坐标 | 回答的问题 | 关键产出 |
|------|-----------|---------|
| **码道 SDD** | "应该怎么做" | 四阶段工作流、规格文件规范、存量分析机制 |
| **Loopra** | "用什么架构实现" | 子 Agent 分工、推理循环、HITL、多模型、工具系统 |

两者的关系：**SDD 定义流程契约，Loopra 提供实现骨架。**

## 二、码道 SDD 四阶段回顾

```
自然语言需求
      │
      ▼
┌─────────────────────────────────────────────────────────┐
│  Phase 1: 需求规格设计（spec-requirement-agent）          │
│  输出：specs/{feature}/spec.md                           │
└─────────────────────────────────────────────────────────┘
      │  spec.md
      ▼
┌─────────────────────────────────────────────────────────┐
│  Phase 2: 实现方案创建（spec-design-agent）               │
│  关键：存量功能关联分析（已实现 / 需扩展 / 需新增）         │
│  输出：specs/{feature}/design.md                         │
└─────────────────────────────────────────────────────────┘
      │  design.md
      ▼
┌─────────────────────────────────────────────────────────┐
│  Phase 3: 编码任务规划（spec-task-agent）                 │
│  关键：拆解为带验收标准的可执行任务，分析依赖关系            │
│  输出：specs/{feature}/tasks.md                           │
└─────────────────────────────────────────────────────────┘
      │  tasks.md
      ▼
┌─────────────────────────────────────────────────────────┐
│  人工审阅闸门（HITL）                                      │
│  用户回复："进入下一阶段"                                  │
└─────────────────────────────────────────────────────────┘
      │  确认后
      ▼
┌─────────────────────────────────────────────────────────┐
│  Phase 4: 任务执行（Coding Agent）                        │
│  关键：生成可编译代码，依据验收条件初步验证，编译修复        │
│  输出：可运行的代码 + 测试                                 │
└─────────────────────────────────────────────────────────┘
```

核心原则：每个阶段只关注自己的职责，Spec 文件是阶段间唯一契约，人工审阅是 Phase 3→4 的闸门。

### 3.2 六大核心机制

| 机制 | 说明 | 在 SDD 中的对应 |
|------|------|---------------|
| **子 Agent 编排** | 不同职责由专门 Agent 负责，主 Agent 协调 | 对应 SDD 四个阶段的四个 Agent |
| **自主推理循环** | 规划 → 执行 → 观察 → 再规划 | Phase 4 任务执行中的编译修复闭环 |
| **HITL 审批** | Human-In-The-Loop，关键节点需人工确认 | Phase 3→4 闸门 |
| **多模型通道** | 支持接入多种 LLM，不同场景用不同模型 | 规格设计用推理模型，代码生成用代码模型 |
| **JSONL 会话持久化** | 完整记录对话和决策历史 | Spec 文件 + 审计追溯 |
| **可扩展工具系统** | harness 层可注册自定义工具 | 编译检查、测试运行、代码搜索等 |

### 4.2 各 Agent 职责详解

#### Spec Agent（需求规格 Agent）

```
输入：自然语言需求描述
处理：
  1. 需求澄清：识别模糊表述，向用户提问
  2. EARS 规则生成：将需求转化为 Ubiquitous/Event-driven/State-driven/Optional/Unwanted 句式
  3. 验收条件定义：每条规则附 [验证动作] → [预期结果]
  4. 职责边界划定：明确"不负责/禁止/不修改"
  5. DFX 约束提取：性能/可靠性/安全性/可维护性/兼容性
输出：specs/{feature}/spec.md
```

#### Design Agent（实现方案 Agent）

```
输入：spec.md + 项目上下文（代码库基线）
处理：
  1. 存量功能关联分析（核心！）：
     - 已实现：项目中已有对应功能，直接复用
     - 需扩展：已有功能需增加新逻辑
     - 需新增：完全新建的代码
  2. 架构设计：模块划分、接口定义、Schema 变更
  3. 生产部署检查清单生成
输出：specs/{feature}/design.md
```

#### Task Agent（任务规划 Agent）

```
输入：spec.md + design.md + 项目上下文
处理：
  1. 任务拆解：按 design.md 拆解为子任务，粒度到文件路径
  2. 依赖排序：分析任务间依赖关系，生成执行顺序
  3. 验收标准绑定：每个子任务附可执行的验收命令和量化目标
输出：specs/{feature}/tasks.md
```

#### Coding Agent（编码执行 Agent）

```
输入：tasks.md（逐任务执行）
处理（自主推理循环）：
  ┌─────────────────────────────────────┐
  │  规划：读取下一个任务，制定实现策略    │
  │    ↓                                │
  │  执行：生成/修改代码文件              │
  │    ↓                                │
  │  观察：运行验证命令（cargo check 等） │
  │    ↓                                │
  │  判断：验收条件是否满足？              │
  │    ├─ 是 → 标记任务完成，进入下一任务  │
  │    └─ 否 → 分析错误，重新规划         │
  └─────────────────────────────────────┘
输出：可编译、通过验收的代码 + 测试
```

## 五、关键设计决策

### 5.1 多模型路由策略

不同阶段使用不同模型，兼顾质量与成本：

| 阶段 | 推荐模型类型 | 原因 | 示例 |
|------|------------|------|------|
| Phase 1 规格设计 | 强推理模型 | 需要理解模糊需求、澄清歧义 | DeepSeek-R1、o3 |
| Phase 2 方案设计 | 强推理 + 代码理解 | 需要分析存量代码、设计架构 | DeepSeek-R1 + CodeLlama |
| Phase 3 任务规划 | 中等推理模型 | 结构化拆解，推理要求适中 | DeepSeek-V3、GPT-4o |
| Phase 4 代码执行 | 代码专用模型 | 高频调用，成本敏感 | CodeLlama、StarCoder |

模型路由由 `loopra-model` 层的 **多模型通道** 统一管理，通过配置切换。

### 5.2 HITL 闸门设计

人工介入点集中在两处：

```
Phase 3 产出 tasks.md
        │
        ▼
  ┌─────────────────┐
  │  HITL 闸门      │
  │                 │
  │  用户操作：      │
  │  · 查看 tasks.md│
  │  · 修改/补充任务│
  │  · 调整优先级   │
  │                 │
  │  确认指令：      │
  │  "进入下一阶段"  │
  └─────────────────┘
        │
        ▼
Phase 4 开始执行
```

HITL 的实现要点：
- 任务清单以结构化格式呈现（Markdown checkbox + 依赖图）
- 用户可在任意任务上添加注释或修改验收标准
- 确认后以最终版 tasks.md 为准执行

### 5.3 Spec 文件持久化

参考 Loopra 的 JSONL 会话持久化，sz-rust AI Agent 的持久化策略：

```
specs/{feature}/
├── spec.md              # Phase 1 产出
├── design.md            # Phase 2 产出
├── tasks.md             # Phase 3 产出
├── session.jsonl        # 完整对话历史（JSONL 格式）
└── artifacts/           # 执行证据
    ├── compile_before.txt
    ├── compile_after.txt
    ├── bench_before.txt
    ├── bench_after.txt
    └── test_report.md
```

`session.jsonl` 记录每次 Agent 交互的完整上下文：
```json
{"role": "user", "content": "实现会员连续登录失败锁定功能", "timestamp": "..."}
{"role": "assistant", "content": "我来分析需求...", "tool_calls": [...], "timestamp": "..."}
{"role": "tool", "content": "存量分析结果...", "timestamp": "..."}
```

### 5.4 工具系统扩展点

sz-rust 的工具系统（harness）需要覆盖以下核心能力：

| 工具类别 | 具体工具 | sz-rust 特有需求 |
|---------|---------|-----------------|
| 文件 IO | 读/写/搜索文件 | tokio::fs 异步 IO |
| 编译检查 | cargo check/clippy | workspace 多 crate 支持 |
| 测试运行 | cargo test | 4556+ 测试，覆盖率门禁 |
| 代码搜索 | grep/ripgrep | crate 级搜索 |
| Git 操作 | diff/commit/log | 铁律合规提交 |
| ORM 操作 | migration 生成 | sz-orm facade |
| Benchmark | criterion | p99 性能基线 |
| Skill 触发 | 调用 sz-rust Skills | routing/middleware/di/config |
| 文档同步 | 检查受影响文档 | 22 条铁律规则 19-22 |

## 六、与现有 sz-rust 体系的集成

### 6.1 与 preCommitCheck Skills 的协作

AI Agent 生成的代码，提交前仍需触发项目配置的 Skills：

| AI Agent 阶段 | 触发的 sz-rust Skill |
|-------------|---------------------|
| Design Agent（含路由变更） | sz-rust-framework-routing |
| Design Agent（含中间件变更） | sz-rust-framework-middleware |
| Design Agent（含 DI 变更） | sz-rust-framework-di |
| Design Agent（含 config/static 变更） | sz-rust-framework-config |
| Coding Agent（编码完成） | sz-rust-test-coverage |
| Coding Agent（含热路径变更） | sz-rust-performance-check |
| Coding Agent（含 pub API 变更） | sz-rust-doc-check |

### 6.2 与 22 条铁律的集成

AI Agent 在 Phase 2（Design）阶段即需检查铁律合规性：

| 铁律分组 | Design Agent 检查项 |
|---------|-------------------|
| 规则 1-3（内存与溢出） | 确认 overflow-checks 配置 |
| 规则 4-6（异步运行时） | 确认无 std::fs，使用 tokio::fs |
| 规则 7-8（安全脱敏） | 确认敏感字段标注 skip_serializing |
| 规则 9-10（性能基线） | 确认 p99 指标可测量 |
| 规则 11-14（数据库安全） | 确认参数化绑定 + 列投影 |
| 规则 15-18（并发模型） | 确认 Send + 'static 约束 |
| 规则 19-22（文档同步） | 确认文档同步任务已列入 tasks.md |

## 八、与 Loopra 的差异点

sz-rust AI Agent 不是 Loopra 的简单复刻，需针对 sz-rust 特点定制：

| 维度 | Loopra（Java） | sz-rust AI Agent（Rust） |
|------|---------------|------------------------|
| 后端语言 | Java + Solon | Rust + Axum/Tokio |
| 桌面框架 | Wails（Go）→ 实际是 Tauri 思路 | Tauri v2（原生 Rust） |
| 编译检查 | Maven/Gradle | Cargo workspace（多 crate） |
| 测试规模 | 常规 | 4556+ 测试，覆盖率门禁 85% |

## 九、总结

本文档建立了 **码道 SDD（流程契约）+ Loopra（实现骨架）** 的融合架构参考：

```
码道 SDD 四阶段          Loopra 六大机制           sz-rust AI Agent
─────────────────   +   ─────────────────   =   ──────────────────
需求规格设计              子 Agent 编排            Spec Agent
实现方案创建              自主推理循环             Design Agent + 存量分析
编码任务规划              HITL 审批               Task Agent + 闸门
任务执行                  多模型通道               Coding Agent + 推理循环
                          JSONL 持久化            Spec 文件 + session.jsonl
                          可扩展工具系统           sz-rust harness（22铁律）
```

3. **人机协同**：HITL 闸门让人聚焦决策，AI 负责执行
4. **质量内建**：验收条件内嵌于任务，执行阶段即验证
5. **可追溯**：JSONL + Spec 文件形成完整审计链
